### Auditability & Context Management
- Maintain the task's own `problem_state.json` (created from `physics-agent/runtime/problem_state_template.json`) as the *only* state source of truth. Its actual top-level fields are: `task`, `stage`, `quota`, `hypothesis_layer`, `dimensional_table`, `knowledge_routing`, `data_source_decision`, `numerical_artifacts`, `audit_logs`, `anomalies`, `verification`, `report` — see `physics-agent/problem_state_schema.md` for the field ownership rules (which node may write which field).
- **Write-back verification (mandatory, applies to every write/edit of `problem_state.json` or any hook-generated artifact)**: after issuing a `write` or `edit` tool call that is supposed to persist a delta into `problem_state.json`, the agent MUST immediately issue a `read` of that same file and confirm the specific field it intended to change now carries the new value (not the pre-edit value, not `null`). A tool call returning "success" does not by itself prove the intended content actually landed — in restricted-permission environments a tool call can be silently rejected or only partially applied, and "the agent thinks it moved to Node X" must never be trusted over "the file on disk actually shows Node X". If the read-back shows the field did NOT update as intended, treat it exactly like a §4 permission shortfall (the write permission the step needed was effectively not available): stop, emit the §4 fixed stop message identifying the specific write that failed to land, and re-request write permission — do not retry the same edit loop indefinitely, and do not mark the node complete in the report based on the tool call's success flag alone.
- Every external capability call (API, physics data, simulation execution, and every `physics-agent/hooks/*.py` invocation) must write a structured audit record via `physics-agent/hooks/audit_log.py` containing `source`, `timestamp`, `args`, and `artifact_id` — do not hand-append to `audit_logs` by any other means.
- **Script-execution audit record (mandatory, ③第 4 条 4b, 10/12 — parallel to the rule above, not an add-on to it)**: whenever an audit record logs the actual execution of a *script* (a `physics-agent/hooks/*.py` invocation, a one-shot solver run, a CLI tool call), that record MUST additionally carry the 6 A4 keys, passed via `audit_log.append_record(..., extras={...})` (the existing 4-key signature is unchanged; these 6 are opt-in, only present when the event being logged is a script execution): `script_path` (relative path of the script file actually invoked, or `"inline"` for a one-shot command that is not a named file) / `stdin_or_argv` (the verbatim command line / input text, **not** a natural-language summary of it) / `stdout_tail` / `stderr` (captured output; the *full* text also lands in a per-run asset file per the 4c rule below — this is not redundant, see that rule's note on what each copy is for) / `exit_code` (the invoked process's actual exit status — note this field's semantic is "the outer command's rc", and the specific handling rule for the #453 `stoppedProcesses` boundary case — outer command returned cleanly but a sub-process it spawned was force-stopped by the platform — is a separate, open decision documented in `dev-notes/网页重新设计1011-共识.md` ③第 4 条 4a's pre-check note, do not silently assume "copy the outer rc" covers that case) / `iteration_index` (which debugging attempt this call was: 1 = first try, 2 = after the first fix, ...). In addition, the record's `args` field MUST include a short `note` key carrying the "作用描述" (a one-or-two-line natural-language description of **what this specific call did for the problem**, not a generic description of the tool itself) — this is written **at the moment the call happens**, not reconstructed later at Node 4 report-generation time (a first-hand description captured in the moment is the only version that can be trusted to match what actually ran; a Node 4-time reconstruction risks drifting from what the script actually did).
- Final numerical conclusions MUST carry a traceability badge pointing at a specific `artifact_id` in the audit log, so the report's claims are anchored to actually-verified intermediate results, not to unverified or hand-stated numbers.
