### Permission Shortfall — Stop-and-Escalate Rule
Several steps in this protocol **require** execution that goes beyond read-only inspection: writing `problem_state.json` deltas back to disk, running `physics-agent/hooks/*.py` as subprocesses (dimensional/boundary gate, audit-log writer, ODE solver), and finally emitting the Node 4 static HTML. If at any point the agent discovers it does **not** have the workspace-modification or command-execution permission a step actually requires — whether because the user never granted it in the first place, or because the user explicitly rejected the agent's execution request for that specific step — the agent **MUST stop the analysis at that point and not improvise a workaround**.

**Distinguish which of the two kinds of "I can't go on" this actually is** (the underlying harness now reports the approval outcome with a reason field, not just a bare reject — do not blur these two cases into one response):

- **Kind 1 — explicitly denied** (`user_rejected`, `policy_denied`): a human or the policy *actively decided* this call should not run. This is a real refusal; emit the fixed stop message in item 3 below and wait for a human decision.
- **Kind 2 — nobody answered** (`timeout`, `no_approver`): the call was not actively refused by anyone; it simply wasn't answered in time, or no client was connected to answer it. This is **not** a decision — it is an absence of a decision. Do **not** treat it the same as Kind 1's "the user said no": do not log it as `permission_denied_by_user` in `anomalies` (that would record a decision nobody made), and do not silently retry the same call in a loop hoping someone is watching. Instead, emit a **shorter variant of the item 3 stop message**, changing only the final "Please grant…" line to:

  ```
  Please confirm whether you were away or do not want this step to run: I could
  not get an answer for {specific permission} (the request timed out / had no
  approver connected). Say "grant it" and I will retry the same call once, or
  say "skip it" and I will record the node as "pending, unanswered" (type
  `permission_unanswered`, distinct from an explicit denial) and close out here.
  ```

  The key difference: Kind 1's stop message already assumes a decision was made and asks the user to act on it; Kind 2's stop message explicitly says **no decision was made yet** and asks the user to make the first one — it must not retroactively label an unanswered request as a rejection.

1. Do **not** substitute "manual re-derivation of what the gate/solver script would have produced" in place of actually running it, and do **not** pretend the step completed on paper when its mechanism (a real subprocess execution) was never exercised — a hand-replayed gate check is not the same guarantee as a gate check that actually ran.
2. Do **not** fabricate or guess at the result of a step it could not actually execute (e.g. inventing what an ODE sweep would have output, or rounding a pending number into a "settled" answer just to finish the report).
3. **Stop and emit the fixed escalation message** — this message is **not** to be freely paraphrased by the agent; the agent only fills in the bracketed fields (`{current node}`, `{specific permission}`, `{completed artifact IDs}`, `{one-line justification}`), which are the only degree of freedom. The rest of the wording is fixed, so that every permission-shortfall stop looks the same and a reviewer can check "did the agent actually stop with the prescribed message" rather than "did the agent sound reasonably sorry about being stuck". **The fixed wording itself (Kind 1 and Kind 2 variants) lives in `physics-agent/knowledge/permission_shortfall_protocol.md` §权限缺口, not here — read that file once for the exact text, do not retype it from memory or improvise a shorter/paraphrased version on the fly.** The rule that governs *when* to use it (the Kind 1 vs Kind 2 distinction above, the "do not hand-replay" rule in item 1, the "do not fabricate" rule in item 2) stays in this file; only the verbatim message body has been moved out.

   - `audit_log.py` itself is a **write-permission** requirement, so this stop message does not depend on being able to run `audit_log.py` first — it is emitted directly as agent output, and *after* the user grants permission, the agent must retroactively log the stop event via `audit_log.py` (type `permission_shortfall_stop`) and the user's grant/denial decision via `audit_log.py` (type `permission_granted` / `permission_denied_by_user`). If the user denies the permission, the agent records that decision verbatim into `problem_state.json`'s `anomalies` (type `permission_denied_by_user`, non-blocking but logged) and states plainly in the report which nodes are "pending user permission" rather than presenting them as complete.
4. **The agent must not resume on its own after emitting this message.** Resumption happens only on an explicit user grant ("yes, you may run the shell now"), or an explicit user denial (in which case the agent closes out with the pending-permission state recorded, not by continuing as if nothing happened). This is what makes the stop a real stop and not just a well-worded pause the agent quietly walks back after.

This rule exists because the project's reliability guarantee comes from **deterministic code actually running**, not from the model claiming it would have produced the same result — a permission shortfall that gets "worked around" by hand-replay silently downgrades the whole defense-line design to something it was explicitly meant to prevent. The fixed message template (item 3) is what makes this enforceable in review: a reviewer can grep the transcript for the exact "⏸ PERMISSION REQUIRED — analysis stopped at Node" header and confirm the stop was actually issued in the prescribed form, rather than trusting the agent's self-report that it "paused briefly".

### Missing Dependency — Stop-and-Escalate Rule (Environment Shortfall, Parallel to §4)
§4 covers "the permission to run this step was not granted"; this section covers a different, equally hard-blocked failure mode: **the step's required runtime dependency is not installed / not reachable in the current environment** (e.g. `python physics-agent/hooks/dimensional_gate.py` fails with `ModuleNotFoundError: No module named 'pint'`, or `node physics-agent/hooks/trace_capture.cjs` fails because no Node.js runtime is available on this machine at all). Do NOT treat a dependency shortfall the same as a normal, fixable code bug, and do NOT improvise around it:

1. **Do not** hand-roll a substitute for a missing deterministic hook — the same core principle as §4 applies: a gate/solver/trace step whose mechanism (a real script execution in the real dependency stack) was never exercised is not the same guarantee as one that actually ran. A `ModuleNotFoundError` on `dimensional_gate.py` means the dimensional check did **not** happen; continuing past that by eyeballing the equation yourself silently downgrades the whole defense-line design, exactly as §4 warns.
2. **Do not** guess a fix and keep going in a loop (e.g. trying `pip install` with a guessed version, or skipping straight to "let's try running the next node instead"). A dependency shortfall is an environment condition, not a code bug, and the agent does not get to unilaterally decide the environment should be different.
3. **Stop and emit a short, plain escalation message** (this one is intentionally shorter than §4's fixed template — it is a report of a concrete blocker, not a permission negotiation). **The exact wording and the four items that must be spelled out concretely (which node/hook/script, which dependency, is installing it a mechanical user-side step, and the A/B options the user can pick) live in `physics-agent/knowledge/permission_shortfall_protocol.md` §环境缺口, not here — read that file once for the exact checklist, do not improvise a free-form variant on the fly.** The rule that governs *when* to use it (the "do not hand-roll a substitute" and "do not loop on guessed fixes" principles in items 1-2 above, and the "log the shortfall itself first" rule below) stays in this file; only the concrete stop-message checklist has been moved out.
   - Log the shortfall itself into `problem_state.json`'s `audit_logs` via `audit_log.py` (`type: "environment_shortfall_stop"`) before emitting the message, so the stop is auditable even if the user never responds — the audit record must exist independently of whether the user's eventual decision lands in the same file later.
4. **The agent must not resume on its own after emitting this message** — same rule as §4 item 4: resumption happens only on the user's explicit "yes, I installed it, run it again" (Option A) or explicit "skip it / mark pending" (Option B), never on the agent quietly deciding the dependency "seemed unlikely to matter" and walking back the stop.

This rule exists for the same reason §4 exists: the project's guarantee is that the deterministic tools **actually ran**, in their real dependency environment, not that the model produced a plausible-looking answer anyway. A dependency shortfall that gets silently papered over is indistinguishable, from the outside, from a run where the gate actually executed and passed — which is exactly the false-comfort failure mode the whole protocol is designed to prevent.

**§4a-0. Portable runtime fast-path (check before declaring a dependency shortfall)**: before treating "Python missing / pip dependency missing" as a §4a stop-and-escalate case, first check whether `physics-agent/third_party/portable-runtime/` (a bundled, project-internal Python 3.13.9 embeddable runtime + pre-baked pinned wheels + CJK font, per `PORTABLE_RUNTIME.md`) can be used **as-is, without touching the user's system** — if so, switch the hook invocation to that portable interpreter (`physics-agent/third_party/portable-runtime/python/python.exe physics-agent/hooks/...`) and continue; only if the portable bundle genuinely does not cover the missing piece (e.g. the missing dependency is one of the explicitly-excluded heavy packages — MinerU, `ambiance`/`pymsis` — see `PORTABLE_RUNTIME.md` §"未纳入本包") does this count as a real §4a environment shortfall requiring the stop-and-wait-for-user flow described above. This fast path exists specifically because the most common real-world "missing Python" case (e.g. a teammate's machine that only has the Windows Store placeholder `python.exe`, as observed in the 4th self-test log) is exactly the case the portable bundle is designed to make a zero-friction, zero-system-tampering answer to — do not route that case into the heavier §4a stop-and-escalate path just because the *system* `python` command is broken, when the project's own bundled interpreter would have sidestepped the problem entirely.

**§4a-0a. Smoke-test before installing: do not run the install step unless the smoke test fails** (companion rule to §4a-0, addresses the specific failure mode of "triggering the install program even though the environment is already complete"): before running any install/reinstall step against the portable bundle (e.g. the `python/Lib/site-packages` install step in `INSTALL.md` §"日常使用"), first run a one-line import smoke test against the portable interpreter itself:
```
physics-agent/third_party/portable-runtime/python/python.exe -c "import sympy, pint, numpy, scipy, matplotlib, plotly; print('site-packages-ok')"
```
- If it prints `site-packages-ok` (the normal state right after a fresh clone, since `site-packages/` ships already populated in the repo): **skip the install step entirely** and go straight to invoking the hook with the portable interpreter. Do not "just in case" re-run the install — a redundant `pip install --target` over already-present packages is not harmless, it is wasted time and a risk of the mixed-version-contamination failure mode observed during this bundle's own build (two different mpmath versions installed into the same `--target` dir, silently not overwriting, until manually cleaned up).
- Only if the smoke test fails with a specific `ModuleNotFoundError` (naming the exact missing module) should the install step be run — and if it fails, run the **exact** install step from `INSTALL.md` §"日常使用" (offline, local wheel, never a fresh network download), then **re-run the smoke test** to confirm it now passes before proceeding to invoke any hook. Do not proceed on the assumption "the install command returned success" without a second, independent import check — the same "tool call success ≠ intended state actually landed" rule that §3's write-back verification applies to `problem_state.json` writes applies here to install steps.
