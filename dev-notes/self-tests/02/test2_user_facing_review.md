# test2（02走查）面向用户问题回顾 — 复核结论

只列“复核过、确认属实”的，没有凭印象列。每个问题都标了“是否已被后续改动解决”。

## 1. **量纲门在 02 走查里"没能跑完"——真实根因比报告里写的更深（后已解决）**

报告/审计日志把失败原因归到"DIM_ALIAS 缺 `area`/`specific_energy` 别名"，但用**完全相同的表达式字符串**
（`du/dx = g - rho*CD*A/(2*m)*u`，dims 里 `u:specific_energy, A:area` 都按当时想喂的值填）对**修复后**的
`dimensional_gate.py` 重跑，结果：

```
{"verdict": "ERROR", "reason": "symbols without declared dimensions: ['du', 'dx']"}
```

不是别名问题（那两个别名现在都已修好，单独喂 `area`/`specific_energy` 都能正常出 `PASS`/`FAIL`），
而是 **`du/dx` 这种手写导数记号 SymPy 直接解析不出来**——它被拆成 `du`、`dx` 两个没被声明的独立符号，
gate 报"未声明维度"后以 `ERROR`（非 `PASS`/`FAIL`）退出，根本没走到量纲比对那一步。
也就是说 02 走查当时是**两个独立 bug 叠在一起**：
(a) 别名表缺口（已在后续修复中确认 `area`/`specific_energy` 现在有效）；
(b) 表达式写法本身用了 gate 没约定支持的手导数记法（**记录时点未修，且 02 走查 agent 当时也没意识到这一层，
   直接把 (b) 归因成 (a) 的"另一种表现"，这个诊断偏差本身是一个值得记录的可靠性问题——agent 自己
   给出的"失败根因"跟实际卡住它的直接原因不完全一致**）。

**影响**：任何以后用户（或新会话里的 agent）把控制方程写成 `du/dx = ...`、`dv/dt = ...` 这种自然导数
记法直接丢给 gate，都会撞同样的 `ERROR`，跟 02 走查一模一样。gate 目前**只接受**"纯代数式"（每个裸
符号单独声明维度、两边直接相减判齐次），要表达导数项必须写成 `Derivative(u, x)` 这种 SymPy 显式
调用形式，但**记录时点没有任何文档/模板/SKILL 指引告诉 agent**
"你的控制方程如果含导数项，喂 gate 之前要先把它写成 `Derivative(...)` 形式而不是手写 `du/dx` 记法"，
这是协议层的缺口，不是工具本身算错。

**建议方向**：在 `SKILL.md` 的 §1"Dimensional Gate"那一条，或者 `dimensional_gate.py` 的
docstring/使用示例里，明确加一句"含导数的方程：把每个导数项写成 SymPy 的 `Derivative(函数, 变量)`
形式再喂给 `--equation`，不要用手写 `du/dx` 记号——这个记法 gate 的 SymPy 解析层不支持"。
（后已落实：`dimensional_gate.py` 的 docstring 与 SKILL.md §1 均已按此补充，本文件保留记录原始发现过程。）

## 2. `node4_pending_note.md` 里"我无法导出本会话 trace"的判断——已被后续工具直接推翻（已解决）

这份 note 白纸黑字写着"当前环境里我（运行 Agent）没有可用的工具导出这份原始 trace"，还给出了"要靠外部
`agh export` 工具"的步骤清单。后续做出来的 `program-design/hooks/trace_capture.cjs` 把这件事做成了
**agent 自己就能一条命令跑通**（不需要任何外部 export 工具，不需要人工下载文件），note 里"需要 3 个步骤
（导出→放到某路径→运行）"的两跳流程现在被合并成一跳。这是本次测试最直接的"用户端能力补齐"成果，
**这一项可以明确标记为已解决**，未来 02 走查这类"trace 拿不到"的卡点不应该再发生。

## 3. 报告的"假伞面积"诊断——本身是好的，但暴露了一个面向用户的真实问题（未解决，跟工具无关）

报告里那段诊断（"领域参数表给的最终亚音速段 A=0.2 m²，比真实降落伞小 75–150 倍，导致峰值过载被高估
3.3 倍"）**写得很好、很诚实**，明确告诉读者"55 km 这个结论是针对这套偏小参数表的，不是通用答案"。
但这是面向用户的一个真实问题：这份 `space_diving_params.json` 里的数值（0.18/0.2 m²）本身就是**出题方
（2023 竞赛题）给定的假设值**，不是一个"真实降落伞尺寸"——agent 把它当作"领域参数"忠实引用并据此建模，
同时又正确诊断出这个参数跟"真实降落伞"的物理常识差距很大。这个"忠实引用给定参数 + 诚实标注它跟现实的
差距"的做法是对的、是好模型该有的表现，**但用户（非物理专业读者）很容易把这个"55 km 是给定参数下的
答案"直接误读成"带降落伞的人从太空下来最安全能到 55 km"**，报告的免责声明写得再好也容易被跳过。
这是一个"模型输出正确但容易被误读"的风险，不是 bug，是**呈现层**的问题（报告末尾那个"可追溯性徽章"
附录只列了 5 个 hash，没有一个"这个结论针对的是哪套参数、参数是否代表真实世界"的一句话总结放最前面）。

## 4. 报告里 artifact_id 用的是"截断"形式（`175025ed...71c3a`），但 `trace_visualizer.py` 的
   cross_check 用的是**完整** 64 位 hash 匹配（未解决）

报告正文里"可追溯性徽章"用的是截断到 `...` 的短 hash（方便人眼读），但 `trace_visualizer.py` 生成 HTML
时做 cross-check 匹配用的是 `problem_state.json` 里存的**完整** artifact_id 去 169 条 tool call 的
args/result 文本里做子串查找。实测（`probe_crosscheck_contents.py`）显示 8 条全 ✅，但这个"全 ✅"
的真实含义是"这个 64 位 hash 字符串恰好出现在某条 tool call 的
文本里"，**不代表"这条 tool call 就是算出这个数值的调用"**——是子串匹配带来的"自举式命中"，不是
"这个数值确实来自这次调用"的语义绑定。这条问题记录时点未动手改，先记下。
