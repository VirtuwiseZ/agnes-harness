## 0. 这个参考文件是什么（一句话）

一个**完全跑在浏览器端、单 HTML 文件、无服务器、无外部资源**的
2D 显式拉格朗日有限元（FEM）仿真器，模拟 APFSDS 动能弹侵彻装甲：
- 7 种材料卡（Johnson-Cook 强度 + JC 损伤 + Mie-Grüneisen 状态方程）；
- 弹芯 + 多层/间隔靶板的结构化四元网格生成，带"剪切跟随"斜角网格优化；
- 中心差分显式时间推进 + 自适应 dt（CFL）+ 沙漏控制 + 侵蚀（单元删除）
  + 空间哈希加速的节点-面段罚函数接触；
- WebGL2 云图渲染（Canvas2D 自动回退）+ 色标/标尺/HUD/探针叠加层；
- `requestAnimationFrame` 主循环 + **每帧子步时间预算**（`substepBudgetMs`），
  让 0.6~17 万单元的算例在特定硬件上保持接近实时；
- 4 档"精度/流畅度"预设（fast/balanced/fine/extreme）：单元数 vs. 每帧预算
  的权衡，超预算自动粗化网格；
- 手动"单步 ×20"模式 + 自动连跑模式并存；
- 一个独立的 **Alekseevskii–Tate 一维解析模型**作为 FEM 结果的**量级对照**
  （不是精度验证，是"穿深量级对不对"的快速交叉检核）。

**重要免责声明（来自文件自身，原话大意）**：材料参数是公开文献中的
**工程近似值**，"用于教学/趋势性仿真，不作弹道鉴定依据"。
—— 也就是说，**这套数字的物理真实性本身没有被验证过**，本笔记也**不采用**
它的材料常数作为本项目数据。用户点名"物理效果真实与否不明确"，与文件
自带的免责声明一致；我们学的是**工程实现技术**，不是它报出的物理结论。

## 1. 真正可迁移的技术（与物理无关，是"怎么在静态单文件里跑活体数值模拟"的通用手法）

以下这些**跟 FEM/侵彻这个具体物理领域无关**，是"浏览器端自包含实时数值
求解"这一类能力的通用配方，值得记住：

1. **每帧子步时间预算（wall-clock budgeted substepping）**：主循环每帧
   不"解到底"，而是"在 `budgetMs` 毫秒内能跑多少步就跑多少步"
   （`APP.simRun(S, budgetMs, maxSteps)`，用 `performance.now()` 每隔几步
   检查一次累计耗时，超了就 break，把剩余子步留给下一帧）。这一步是把
   "重数值模型"变成"浏览器里还能实时交互"的关键 —— 不是把模型做快，
   而是**把一帧能负担的计算量设上限**，用多帧时间换总进度，让渲染循环
   （`requestAnimationFrame`）不卡死。
2. **精度/流畅度档位（quality tiers）**：不是一把梭"算得精"或"算得爽"，
   而是把网格规模（`budget` 单元数上限）、时间步安全系数（`tssf`）、
   接触重建频率（`contactEvery`）、沙漏系数等**成组打包成几个档位**，
   每个档位标注"大约多少单元 / 大概实时不实时 / 能看清到什么程度"
   （fast ≈ 0.6~1.4万单元、extreme ≈ 12~17万单元"仅用于出图，单次数分钟"）。
   超预算时网格**自动粗化**（`h *= sqrt(ne/budget)*1.02` 循环 8 次尝试），
   并在 UI 上明确提示"⚠ 已自动粗化到 h=…"—— 不静默牺牲精度，把取舍
   对用户可见。
3. **手动单步模式与自动连跑并存**（`btnStep` = "单步×20"，`btnRun` = 自动
   播放/暂停）：给读者"逐帧看物理过程怎么演化"的调试/教学能力，不是
   只能看结果。
4. **WebGL 优先 + Canvas2D 回退**的渲染器设计：`getContext('webgl2')`
   拿不到就自动降级到 2D 逐格填色，功能一致（色标/HUD/叠加层共用），
   只是性能差一档 —— 不因为目标机器没有 WebGL2 就整个打不开。
5. **一维解析模型做"量级对照"**（Tate 模型 vs. FEM 结果）：不追求逐点
   吻合，只用来回答"穿深度量级对不对"，是**数值结果的健康检查**，
   不是精度证明。这条"配一个便宜的独立解析模型当粗检"的思路，跟本项目
   里"用 Python 参考实现逐点核对 JS 重算"（见 `interactive_live` kind 的
   JS-vs-Python 数值对比验证）是同一个"不静默、要交叉核对"原则，只是
   场景不同（那个是 JS 数值正确性，这个是 FEM 量级正确性）。
6. **时间历史曲线（`S.hist`）随仿真推进滚动记录 + 双图表实时刷新**：
   侵深/余长 vs. 时间、弹速/动能 vs. 时间两条随播放实时更新的曲线，
   不是仿真结束后才出图 —— 交互与监控同屏。

## 2. 明确不迁移、以及为什么（这是本笔记最要紧的结论）

**不把这套 FEM 搬进 `make_report_figures.py`，也不新增一个"实时 FEM 仿真"
figure kind。理由：**

1. **它是一个专用物理仿真器，不是通用图表能力。** 本项目 `make_report_figures.py`
   的 8 种 figure kind（curve/scatter/error_bar/interval_highlight/heatmap/
   boxplot/interactive/interactive_live）服务的是"把**已经算好的数值结果**
   画成图/可切换/可调参"这一层，不是"在浏览器里跑一个 2000 行的
   专用求解器"。把后者的 2000 行领域代码（网格生成、接触、JC 本构、
   沙漏控制、WebGL shader）塞进通用绘图管线，等于给通用工具挂了一个
   巨大的、只有这一道题用得上的专用引擎 —— 直接违反本项目一贯的
   "克制 / 最小改动 / 不扩大成通用脚本环境"原则（`interactive_live`
   kind 的 `js_function_body` 沙箱边界就是这么定的，见
   `dev-notes/interactive_figure_design.md` §6、`charting_generic_architecture.md`
   §10 对"JS 作用域刻意保持窄"的说明）。
2. **它的物理结论未被验证，文件自身也声明"不作弹道鉴定依据"。** 学"怎么
   实现"是安全的；把"穿深数值""材料常数"当成可信数据带进本项目，
   与本项目"数据要有可核查来源、不静默"的原则冲突。本笔记明确**不采用**
   任何 `MATERIALS` 卡片里的 `rho0/A/B/n/D…/pSpall` 等数值作为本项目数据。
3. **`interactive_live` kind 现有边界（"只能闭式重算，不能实时重解
   ODE/PDE"）仍然是对的、不用改 —— 原因比之前想的更细**：
   - 之前把这条边界当成"浏览器做不到"，其实**是"通用绘图管线不值得为
     一道题挂一个专用求解器"的范围选择**，不是技术硬上限。本参考文件
     证明"浏览器端真能实时跑重数值模型"这条路在原理上是通的（预算
     子步 + 档位 + 手动单步那套配方）。
   - 但把它做通用化，意味着通用管线要能承载任意重数值求解器，成本/
     边界/可维护性都远超本项目当前"画已算好的结果"定位。**因此结论是：
     现有边界保持不动**（继续如实写着"不重解重模型"），只是在这条边界
     旁边**加一句脚注**："这条边界是范围/成本选择，不是浏览器技术
     做不到；已知存在自包含实时重数值仿真的可行做法（本参考文件 +
     本笔记 §1 的 6 条配方），如果将来某道题**确实**需要一个能实时重解
     的专用数值模型，应**单独立项评估**是否值得为那一类题目引入一个
     独立的、带自己依赖与沙箱边界的重型 figure 分支，而不是把重型
     求解器混进现在这条"画已算结果"的通用管线"。
   - 一句话：**边界不改，但把"为什么这么定"说得比"浏览器做不到"更准确
     （是范围选择不是能力硬上限），并指向这份笔记，供未来真遇到那种
     题时查阅，而不是凭旧印象当成铁律。**

## 3. 落地动作（本笔记实际做了什么）

- 本笔记文件（本节所在位置）—— 完整的技术拆解 + 不迁移的理由。

  边界）之后追加一节"边界性质澄清 + 指向本笔记"，只加边界性质澄清，
  不改 §10 已经写好的"只做闭式重算"这条硬边界本身，那条继续成立，
  继续写在 schema 的 live_model_note 字段里。

- 代码层：本笔记 §1 的通用配方已经真正落进 make_report_figures.py 的
  _render_interactive_live()，全部是可选、向后兼容的增强，不改动现有任何
  必填字段，现有 demo 的行为不变：

  1. 新可选字段 y_range_pin，取值是两元素 lo, hi，钉死 y 轴量程，避免
     Plotly.restyle 每次滑块拖动都触发自动量程重算导致的轴抖动。对应
     本笔记 §1 第 1 条的通用化，参考文件的 autoRange 时间平滑在这里用
     "固定区间"而不是"移动平均"实现，因为我们这条曲线是一维静态重绘，
     不是逐帧滚动仿真。缺省时行为跟之前完全一样。
  2. 状态条三态外露，替换原有"只有出错才显示一行红字、平时空白"。对应
     本笔记 §1 里状态/诊断可见的思路，参考文件 sim.done、reason、running
     的三态外露。现在空闲时显示"正常：曲线已按当前参数实时重算…"，出错
     时仍显式报出原因，不再静默。只是把正常状态也如实说出来，不改变
     "出错必须可见、不许静默"的既有原则。
  3. 新可选字段 verify_reference_js、verify_reference_value、
     verify_reference_label。对应本笔记 §1 第 5 条"便宜解析模型做量级
     对照"的通用化，允许在 spec 里带一个上游独立算好的参考值或 JS
     表达式，JS 端实时显示当前闭式结果网格均值对比独立参考值的偏差，把
     上一轮已经落地的 JS-vs-Python 数值正确性核对从构建时一次性检查
     升级成读报告的人也能当场看到的常驻对照读数。JS 表达式若提供，同样
     受 js_function_body 那套沙箱约束，无 DOM、fetch、eval、网络。

## 4. 一句话总结

学的是"静态单文件里跑活体数值求解"的通用配方；**不学**的是"把某道具体
物理题的专用求解器塞进通用绘图管线"。`interactive_live` 现有"只做闭式
重算、不重解 ODE/PDE"边界本身保持不动，这一轮额外做了三件来自该参考文件
通用交互模式的小增强，全部可选、向后兼容、不扩大 JS 沙箱边界：钉死 y
轴量程（`y_range_pin`）、状态条三态外露（正常/出错都显式可见）、可选的
独立参考值对照读数（`verify_reference_*`）。
