## 2. 候选技术方案，逐个评估

### 方案 1：扩展 `trace_visualizer.py` 已有的 markdown 渲染器，让它支持"图"
- 现状：`trace_visualizer.py` 把 `report_<slug>.md` 渲染进 HTML，但**只处理 markdown
  的有限子集**（标题、段落、列表、代码块、表格），没有图片/图表通道——`developer_feedback_
  2025B_artillery.md` F4 已经诊断过这个根因。
- 改动量：需要给这个渲染器加一条"行内图片/内嵌图表"的解析路径，或者约定一个
  "报告里只能放一张 base64 内联 SVG/图片，放在特定标记里"的窄约定。
- 优点：改动集中在项目自有的一个确定性脚本里，跟"确定性防御线"精神一致。
- 缺点：markdown 渲染器本身不是干这个的，硬塞图表进去会越写越复杂，跟这个项目
  "报告层呈现要克制、不炫技"的方向不太合。

### 方案 2：报告正文（markdown）里直接写"要画哪些图"的说明，由一个新的小脚本
`make_report_figures.py` 在 Node 3 生成报告**之前**从 `problem_state.json` 的
`numerical_artifacts` 里读数据、生成 SVG 文件（每张图一个 `.svg`），报告正文里用
`![](...)` 或约定的"图注"引用这些 SVG 文件名；`trace_visualizer.py` 只需最小改动：
遇到报告里引用的 SVG 文件名，把它按 base64 内联进最终 HTML（这样最终 HTML 仍然是
"自包含单文件"，符合项目"绝对只读前端"原则，不需要额外部署图片服务器）。
- 优点：**职责分得很干净**——画图的逻辑（读哪个字段、画哪种图、坐标轴怎么标）全部
  落在一个纯函数式的、可单独测试的新脚本里，跟"量纲门/边界门/审计日志"同构
  （确定性、可复现、不依赖 LLM 现场发挥）；`trace_visualizer.py` 只需要加一条很窄的
  "遇到 SVG 文件名就内联"的改动，不碰它现有的 markdown 渲染逻辑。
- 缺点：多一个要维护的脚本；SVG 生成需要选一个绘图库（见 §3）。

### 方案 3：报告正文里直接让 LLM 现场写 SVG 代码
- 优点：不用新写任何脚本。
- 缺点：跟项目"确定性防御线"的整体方向背道而驰——让 LLM 现场手写 SVG 坐标轴/
  曲线，等于把"验证过的数值结果"又交给了一层不可审计的自由发挥，跟"量纲门拦到
  单位错误"这套设计的初衷（"保证靠确定性程序跑出来，不靠模型现场编"）直接冲突。
  **不建议**，列出来只是为了说明为什么排除它。

### 方案 4：报告正文写数据，HTML 侧用 JavaScript 现场画图（比如塞一段 Plotly/
Chart.js 进 HTML，浏览器打开时动态渲染）
- 优点：交互性最好（可以放大、悬停看数值）。
- 缺点：跟"绝对只读、静态、单文件、不写任何东西"的现有原则有张力（虽然技术上不
  冲突，JS 动态渲染不等于"写回文件"）；更重要的是引入一个前端 JS 依赖，跟项目
  目前"零第三方前端依赖"的状态相比是个明显的复杂度升级，且"用户点开浏览器才画
  出来"意味着截图/打印/离线查看的行为会变差。**目前不推荐作为首选**，可以作为
  "以后如果想做交互版报告"的备选，不跟本次一起做。

## 3. 如果走方案 2，SVG 用什么生成

两个现实候选，都不引入重量级依赖：
- **Matplotlib 直接存 SVG**：项目已经在用 Python 科学计算栈（SymPy/numpy/scipy），
  装一个 `matplotlib` 不增加什么负担，`savefig('xxx.svg')` 一行出图，质量稳定，
  曲线/散点/坐标轴/图例全是现成的。缺点：SVG 里会带 matplotlib 默认的一堆内嵌
  样式，文件比手写的"裸 SVG"大几十 KB（对"自包含单文件 HTML"来说完全可接受，
  不是问题）。
- **手写 SVG 字符串**（`write_svg_figure.py` 里自己拼 `<svg>`/`<path>`/`<polyline>`
  片段）：零依赖、产物更小、完全可控（坐标轴刻度/标注文字全部自己决定，不会出现
  matplotlib 默认字体/配色跟报告整体风格打架的问题）。缺点：多张图（弹道叠图、
  单调性曲线这种带多条线/数据点的图）手写字符串会开始变得冗长难维护，超过
  "三张以内"的场景，维护成本会超过直接装 matplotlib。

**初步倾向**：`make_report_figures.py` 里允许两种后端，默认用 matplotlib（覆盖
  绝大多数场景，一行代码出图），如果某张图需要特别精确控制（比如"只在频带区间
  高亮、其余灰色"这种需要手工指定填充区域的 Sasando 模态图），走"手写 SVG 字符串"
  这条备选路径，两个后端产物都是同一个 `.svg` 文件，`trace_visualizer.py` 的内联
  逻辑完全不感知后端差异。这个选择本身不影响主架构，先记下，等真正写
  `make_report_figures.py` 时再定。

## 4. 跟已搁置的 `artifact_id`/哈希呈现方案的关系

本方案跟共识备忘录第 1 条（`artifact_id` 哈希呈现搁置/可能放弃）**不冲突、不依赖**：
图表走的是"报告正文（Node 3 markdown）→ 数值字段（problem_state.json）→ 确定性
脚本生成 SVG → 内联进 HTML"这条链，全程**不需要** `cross_check()` 子串匹配
artifact_id，也就不受那个"全 ⚠/全 ✅ 都不代表真的语义绑定"的设计缺陷影响——
换句话说，即使最终 `artifact_id`/哈希这套呈现真的被整体砍掉，本方案照样成立、
不需要跟着改。
