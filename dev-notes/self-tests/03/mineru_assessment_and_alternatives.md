# MinerU 实际使用评估 + 更便捷替代方案评估

## 1. 本次 5 篇 PDF 实测：速度瓶颈在哪

| 篇 | 页数 | 本机 `basic` 档耗时 |
|---|---|---|
| 2025-GM-A-112 | 26 | 75 s |
| 2025-GM-A-182 | — | ~75 s |
| 2025-GM-B-127 | — | ~130 s |
| 2025-GM-B-796 | 52 | 337 s |
| 2025-GM-B-765 | 26+ | ~130 s |

合计约 12 分钟跑完 5 篇，其中 52 页那篇（796）单独 337 秒 —— 这是撞到我 shell 单次调用 600 秒
上限的原因（"太慢"的直接体验）。速度瓶颈是**本机 ONNX/CPU 推理**（`basic` 档在本机只能跑
ONNX 引擎，`standard`/`advanced` 需要 8GB+ 显存走 PyTorch/vLLM，本机 RTX 4050 只有 4GB，
**够不到**），不是网络或 I/O 问题。

## 2. 跟"之前处理 3 篇论文"用的方法相比，MinerU 好在哪、差在哪

**之前（02 走查及更早）用的方法**：agent 直接用 `web_fetch`/肉眼读 PDF 文本，或者让用户自己
把 PDF 里的关键数字/公式**手动敲进 prompt**，没有专门的文档解析环节。

| 维度 | 之前（手动/web_fetch） | 本次（MinerU 本地 basic 档） |
|---|---|---|
| **公式提取** | 基本拿不到可解析的 LaTeX，只能靠人眼读 | 自动转 LaTeX（本次 5 篇 latex 符号命中 24–248 处/篇，全部机器可读） |
| **表格提取** | 手动敲 | 自动转 markdown pipe 表格（本次 51–67 行/篇） |
| **图片/图注** | 只能描述"这张图大概画了什么" | 自动抽出 15–35 张内联 base64 图片 + 图注（本次 5 篇全有） |
| **可回溯定位** | 没有 | 官方 `doc:.../page:.../block:...` 定位器（本次没用到，但能力在） |
| **一致性/可复现** | 每次人眼读都不一样 | 同一输入同档位，输出可复现（本地缓存 SHA256 去重） |
| **速度** | 快（没有解析环节） | **慢**（本次实测的痛点，单篇 75–337s） |
| **是否需要 GPU/显存** | 否 | `basic` 档 CPU 就够，但速度瓶颈就卡在这里；`standard`/`advanced` 本机跑不动 |

**结论：MinerU 换来的价值是"公式/表格/图片全部机器可读且可回溯"，这是之前完全没有的能力，
值得为它付这个时间成本；但"本机 CPU 推理"确实是主要拖慢点，5 篇合计 ~12 分钟这件事可以
接受（一次性、后台可跑），但**不适合当成"边分析边反复解析同一篇文档"的高频操作**——同一篇
文档解析过一次之后，MinerU 的 SHA256 缓存会让第二次几乎瞬间返回，所以"慢"只发生在"第一次
解析某篇新文档"这个点上，不会每次都慢。**

## 3. 对"本项目用户"（提出物理问题的非程序员）而言，更便捷的文档处理方案评估

按"能不能落地到 AGH 的 Skill/MCP 体系里、不用用户手动敲数字进 prompt"这个标准重新排：

### 3.1 继续用 MinerU（本次选的路）
- **优点**：官方 Skill 已经把安装/错误码/续读/隐私规则全写好，直接导入即可用；公式/表格/
  图片提取质量在本次实测中验证过关（5 篇全无乱码，唯一小瑕疵是 796 里代码注释被误判成
  markdown 标题，不影响正文物理内容）；SHA256 缓存让"同一篇文档反复读"几乎零成本。
- **缺点**：首次解析慢（本机 CPU）；`basic` 档在本机 4GB 显存机器上是能跑的**天花板**，
  想要 `standard`/`advanced` 只能走远程（需 API Key + 上传，涉及隐私/版权题面文件是否
  可上传，需用户明确同意，不能默认做）。
- **适用场景**：题面/数据源本身是"格式复杂、公式表格多"的文档（PDF 论文、docx 实验报告、
  扫描件）——这正是本次 5 篇范文的典型情况，也是"物理题"最常见的输入形态。

### 3.2 不装任何重依赖，走"用户手动喂关键数字"这条老路（02 走查前一直在用的）
- **优点**：零安装成本，agent 不需要任何文档解析能力，用户直接把"98–1047 Hz""70 cm 竹管"
  这类题面数字敲进 prompt 就行。
- **缺点**：**这正是本次要解决的问题本身**——用户明确要求"PDF/docx/扫描件这种格式复杂、
  公式/表格多的文档，让 AI 直接读，不要让用户手动敲"。这条老路在新需求下已经不够用了，
  不推荐再作为主方案，只作为"用户手里确实只有一个纯文本题面、不涉及任何文档格式"时的
  兜底路径。

### 3.3 走 MinerU 官方远程解析（`--remote`，`standard`/`advanced` 档）
- **优点**：本机 4GB 显存跑不动的高档位（`standard` 质量明显比 `basic` 好，`advanced` 是
  最高质量）只有远程能提供；速度上远程通常比本机 CPU 推理快很多（服务端多卡）。
- **缺点**：**题目原文/实验数据会上传到 mineru.net 官方服务器**（官方文档明确：本地解析
  失败/档位不够时"不能静默 fallback 到远程"，必须由用户明确同意才能上传）；本次 5 篇是
  IPhO 官方范文，涉及版权/隐私的话**不应该默认上传**；需要 API Key（注册用户配额更高，
  匿名用户配额低但够用做一次性测试，但配额会耗尽）。
- **适用场景**：用户**明确**说"这些文档可以放心上传"且本机跑不动的档位时才启用，**绝不
  默认启用**。

### 3.4 完全不装 MinerU，改用一个更轻的"PDF 纯文本抽取"工具（如 `pypdf`/`pdfplumber`
直接调用，不走 MinerU 的模型推理）
- **优点**：极快（毫秒级，不需要 ONNX 推理），零显存/占用。
- **缺点**：**只能抽纯文本，公式/表格/图片全部丢失**——正好是本次需求里"公式/表格密集"
  这个核心痛点最不能接受的处理方式（题目里的 `f = n·v/(4L)`、阻力系数表、弹道图都会被
  抽成乱码或完全丢掉），不推荐用于"公式/表格密集"的文档，只推荐用于"基本是纯文字、
  不含公式表格"的文档（比如纯文字的实验流程说明）。
- **结论**：跟 3.1 不是替代关系，是**互补关系**——可以写进协议"先快速判断文档是
  '纯文字'还是'公式表格密集'，前者用 3.4 的轻量抽取（快），后者才动用 MinerU（慢但全）"，
  避免每次都走 3.1 这个重路径。

### 3.5 直接把"PDF/图片转 Markdown"这件事交给用户自己用现成工具（如 MinerU 桌面端、
  在线转换网站）转好，把转好的 `.md` 文件喂给 agent，agent 只负责读现成 markdown，
  不自己做解析
- **优点**：agent 侧完全不需要装 MinerU（或任何重依赖），本次我手动跑解析这一步可以
  完全省掉，用户拿到 5 篇范文时自己转成 5 个 `.md` 直接给我读就行；速度上"用户自己
  什么时候转"不受我这边超时/环境限制。
- **缺点**：把"解析"这件事的可靠性责任转移给了用户（用户转出来的 `.md` 公式/表格质量
  好不好，我这边没法保证，只能靠用户自己目测一遍）；如果用户本身就不熟悉这些工具，
  等于没帮上忙。
- **结论**：**跟 3.1 是"谁来做解析"的分工问题，不是技术方案问题**——如果用户愿意自己
  转，3.5 是本次实际走的路（我这边手动跑了一遍 MinerU 生成 5 个 `.md`，等价于"用户
  转好喂给我"这个动作由我代做了一次）；以后如果是常态化使用，建议**明确写进协议
  "用户自己转好喂 md 文件，agent 不代做解析"作为默认路径**，agent 侧的 MinerU 能力
  只作为"用户确实没有现成 md、只有原始 PDF 且坚持要 agent 自己读"时的兜底路径，
  而不是每次都默认 agent 自己去跑一遍慢解析。

## 4. 对本项目的建议（可写进协议/共识备忘录，待你确认后才动手）

1. **默认路径改为 3.5（用户自己转好喂 md，agent 不代跑解析）**，把"agent 自己跑 MinerU"
   降级为兜底路径（用户手里确实只有原始 PDF/图片、且明确说"你直接读"时才走）。这样
   既保留 MinerU 已经验证过的"公式/表格/图片全提取"能力，又不用每次都付 75–337s 的
   时间成本。
2. **加一条"文档快/慢两档分流"规则**（3.1 与 3.4 的互补）：agent 先判断文档是
   "纯文字"还是"公式/表格密集"，前者直接用轻量纯文本抽取（`pypdf`/`pdfplumber`，
   毫秒级，不装 MinerU 也行），后者才动用 MinerU（需要时再装/确认已装）。
3. **远程解析（3.3）保持"必须用户明确同意才能启用"的硬规则**，不默认启用，理由：
   题面/范文可能涉及版权内容，上传是用户自己的决定，agent 不能替用户做这个决定
   （跟本次 §4 "权限缺口"停止规则的精神一致，是隐私边界上的同类问题）。
4. 以上 4 条都还没写进 `physics-agent-governance` SKILL 或共识备忘录，**待你确认后**才
   动手改，本次只做评估，不擅自改协议。

## 5. 一个诚实的、需要说明的限制

- 本次 5 篇范文的解析**全部由我在后台手动跑 MinerU 完成的**（不是 agent 在正式做题流程里
  "自己判断该用 MinerU"跑出来的）——也就是说，"agent 会不会在需要解析文档时真的自动想起
  并正确调用 MinerU"这个协议层面的行为，本次还没有在正式做题场景里测试过，只测试了
  "MinerU 本身能不能把 5 篇文档解析成可用的 md"这一层。等下一步把 3.5/分流规则写进协议后，
  需要再走一次完整做题流程（给一道新题 + 一份 PDF 题面，看 agent 会不会按新规则正确
  分流），才能真正验证"agent 侧的行为"这一层，不只是"MinerU 本身"这一层。
