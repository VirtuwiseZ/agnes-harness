## 一、协议机制层面：本轮新增的几项协议改动，全部被真实执行，不是走过场

| 机制 | 2025A（Sasando，音板） | 2025B（火炮） |
|---|---|---|
| `session_key` 自动写入 | `2da33c6e-...`（真实值，非占位） | `5f6ef764-...`（真实值，非占位） |
| `internal_prior`（Node 1a 私有先验） | 一段真实的量级直觉草图（"f₁ 大概在 100–400 Hz"），不是空话 | 一段真实的量级直觉草图（"v₀ 大概在 110–130 m/s，风是次要修正"），不是空话 |
| `internal_prior` 与 Node 2b 结果的偏差检查（`internal_prior_divergence`） | 真实做过，且**如实记录"无实质偏差"**（先验 100–400 Hz vs 实际 212 Hz，落在范围内） | 报告未专门展开做偏差检查（Node 2b 出结果后没有对应 audit_log 记录）——**这是 2025B 相对 2025A 的一个执行不一致点** |
| Node 2a `mechanism_match_check`（"张冠李戴"防护） | 逐条审完，明确判定"拖曳 ODE/CD 马赫数模板的具体假设全部不适用、不沿用" | 逐条审完，明确判定"模板的 1D 掉高距离坐标 ODE 不适用、CD 值不适用，重推为 2D 命中条件" |
| Node 1 题目专属参数表（`task_params_template.json` 派生） | `sasando_resonator_params.json`，且正确**省略了不适用的块**（无 aerodynamic_or_coupling_coefficients，无 atmosphere 数据源块） | `artillery_params.json`，同样按题面实际需要的量填写 |
| `trace_capture.cjs` 自动 trace 抓取 | `trace_capture_converted_2da33c6e.jsonl`（149 行，112 条 tool call） | `trace_capture_converted_5f6ef764.jsonl`（147 行，112 条 tool call），全程无人工 `agh export` |

**结论**：上一轮为"泛用性"加的协议机制（内部先验、机制匹配、参数表模板、session_key 自动记录、
自动 trace 抓取）在**完全陌生的物理机制**（弹性薄板振动，跟 2023 高空跳伞 / 2025B 弹道都没有
共同词汇表）上依然被 agent 真实执行且执行质量高，这是本轮测试最重要的正面结论。

## 二、量纲门 / 边界门：两道题都真实跑通，且 2025A 上真的拦到了一次单位错误

- **2025A（Sasando）**：模态 ODE 第一次写成"右端是集中总力（force）"的量纲，被量纲门如实
  判 **FAIL**（左端惯性/阻尼/刚度项是面力量纲 mass/(length·time²)，右端 force 是
  mass·length/time²，不匹配）——agent 没有绕过，诊断出"模态方程必须做面积归一化，右端应是
  等效面压强 p_m 而非总力 F_m"，修正后**再次通过量纲门禁**才进入数值计算。这是本轮测试
  里最理想的一种表现：门真实拦到了一次单位混淆，且拦截结果被如实记录、当场修正，不是
  "门没跑通所以没验到"（对比 02 走查那个"别名缺口 + du/dx 记法"双重 bug 导致门根本没跑起来
  的老问题）。
- **2025B（火炮）**：4 条 ODE 全部量纲 PASS；边界门 4 个退化 case + 7 点单调性扫描全 PASS，
  且抓到"CD=0 真空极限"和"v₀ 单调性"两个真实的物理敏感信号，不是照模板数字打勾。
- **两道题都没有复现 02 走查那个 `du/dx` 手写导数记法坑**——2025B 用的是手写 `dvx/dt`、
  `dvz/dt` 这种**时间导数**（不是 02 走查那种"对掉高距离 x 求导"的非标准写法），SymPy 直接
  能解析，没撞上"必须写成 `Derivative(...)` 形式"的那条边界。换句话说：**上一轮预判的
  "下一道含导数项的新题会不会重蹈 02 走查的记法坑"，这次没有复现，但不能说这条隐患已排除**
  ——如果哪道题的方程本身是"对某个非时间自变量求导"（比如 02 走查那种 `dv/dx` 对掉高距离
  求导的形式），大概率还是会撞上，目前只能靠"写进 docstring 的指引"这条软防线兜着，还没有
  在代码层加自动检测（这条上一轮就挂着，本轮维持不动，等下一道真正撞上再决定要不要升级成
  硬拦截）。

## 三、运行流程里的顺利点（具体到可复述的细节）

1. **审批"故意出问题"场景（2025B 全程）里，agent 没有硬闯**：用户记录里 shell/write/edit 审批
   被反复超时/拒绝，agent 每次都用"⏸ 协议规定的停止消息"形式停下来说明情况，而不是绕过审批
   硬跑。这是 §4 停止规则在真实"反复受挫"压力下的正面测试，agent 没有破防。
2. **2025B 里一个 0 字节文件损坏被当异常如实处理，没有静默吞掉**：`problem_state.json` 被一次
   低级脚本错误（open-for-write 后没读到内容就写回去了）截断成 0 字节，agent 没有装作没发生，
   而是按 §3 的"write-back 校验失败当 §4 权限缺口处理"的思路，把整个文件状态从更早的脚本输出
   里重建回来，并在 `problem_state.json` 的 `_note` 字段和 `anomalies` 里如实记录了这次重建
   （"Reconstructed after a failed write attempt... This is logged as an anomaly, not silently
   papered over"）——这跟 02 走查里"门根本没跑通就往下走"是完全相反的处理方式，说明协议里
   "不许静默 paper over"这条在两道题上真的被遵守了。
3. **`dev-notes/` 隔离规则在 2025B（审批出问题那次）里没有被违反**：trace 里没有任何对
   `dev-notes/self-tests/` 的读取尝试（那个 worktree 本身已经被用户 `git rm -r dev-notes/`
   删掉了，所以物理上也没得读；但更重要的是 agent 没有"试图去读一个不存在的 dev-notes"，
   说明它确实把这条隔离规则当成了硬约束而不是"没看到就不知道"）。

## 四、运行流程里的不足点（具体到可复述的细节，按"能不能改/该不该现在改"分两类）

### 4.1 报告呈现层的问题（详见已 commit 的共识备忘录
`dev-notes/architecture/project_consensus_03_report_redesign.md`，本节只列条目）

- `artifact_id` 哈希码作为面向用户的呈现手段：实测体验"乱乱的、只能看不方便查、并不让人
  感觉靠谱"，且"点击哈希跳到对应 AGH 运行记录"这条路目前根本没有被实现过（只有 seq 数字，
  没有可点开的目标）。**共识：这套哈希呈现方案搁置，可能整体放弃**；`cross_check()` 那个
  "子串匹配 ≠ 语义绑定"的已知设计缺陷也不再单独立项修，等新呈现方案定下来一起考虑。
- 报告反复强调"结论 ↔ 运行步骤对应"但对应本身不方便核对，主次颠倒。**共识：正文用人话直接
  说"这一步跑了什么脚本、输入是什么、得到什么结论"，把"点开看原始调用"降级成可选的、深藏
  一层的附加信息，不是默认语气。**
- 报告语言不跟提问语言一致（中文提问出了全英文报告，SKILL.md 现在只有一句很弱的"in the
  user's language"）。**共识：SKILL.md 写死"报告正文语言 = 用户提问语言"，中断说明同样适用。**
- 报告里出现 agent 自言自语式措辞（"这一点必须在最终结论里明确写出，不能藏在代码里"被原样
  带进给用户看的正文）。**共识：Node 3 加一道规则——给自己的后续提醒不能写进
  `report_<slug>.md` 正文，要留就写进 `problem_state.json` 的独立内部字段。**
- `program-design/runtime/` 下多个会话的产物平铺在同一目录，实际造成了 2025A 报告里提到
  2025B 的跨任务串档。**共识：改成 `program-design/runtime/<task-slug>/` 按任务分子目录。**
- 报告/产物路径太深（`program-design/runtime/` 下 4 级），用户得进文件管理器逐层翻。
  **共识：至少让 agent 在回复里给一个 `file:///` 可直接粘贴进浏览器的链接（AGH 前端
  做不了会话内可点链接时的兜底），产物目录也考虑放到更浅的位置。**
- 报告里缺乏仿真数据图表（只有文字 + 简单 markdown 表格）。**共识：方向认可、要认真做，
  但不是现在做，等本轮流程质量分析做完、上面几条共识落地后单独立项。**

### 4.2 运行流程本身的细节问题（跟报告呈现无关，是"agent 干活的过程"层面）

1. **`audit_log.py` 被以非规定方式调用失败（2025A）**：trace 里有一条
   `audit_log.py: error: unrecognized arguments`——agent 试图用"把所有参数平铺成一串"的方式
   调 `audit_log.py`，而不是按它规定的 `append`/`verify` 子命令结构调，被 argparse 拒了。
   这说明**agent 对钩子脚本的调用约定（不是协议本身，是脚本的 CLI 契约）理解得不够扎实**，
   跟"协议该不该加什么步骤"无关，是"写钩子脚本时要在 docstring 里把可运行的完整命令行示例
   放得更显眼"这个层面能改善的（上一轮已经在 `dimensional_gate.py` 的 docstring 里做过同款
   处理，`audit_log.py` 还没做，是同一类问题的下一个实例）。
2. **`ambiance` 库的 API 第一次用错（2025A）**：`ambiance.Ambiance()` 报
   `AttributeError: module 'ambiance' has no attribute 'Ambiance'`（正确用法是模块级函数，
   不是类）。这类"第三方库 API 猜错"的问题，agent 当场发现并修正了，没有隐瞒，处理得当；
   但**这个纠错本身没有作为一次独立的 `audit_log` 记录沉淀下来**（只是跑了一次失败的 shell
   就换写法重试了），意味着"数据源确认可用"（Node 1.5 的 `availability_check`）这一步的
   证据链里，"第一次 import 失败"这个细节没有进审计记录，只有"最后跑通的那个调用"进了。
   这是 `audit_log.py` 使用上"哪一步算一次独立的审计事件"边界还不够清晰的体现，先记下，
   不用现在改协议，下次做 `audit_log.py` CLI 契约说明时一并考虑要不要在 docstring 里写清楚
   "每次独立的可用性探测都算一条 `availability_check` 记录，即使第一次探测失败"。
3. **2025B 里 `node1_audit_setup.py` 因为 `import audit_log` 找不到模块路径而失败两次**
   （`ModuleNotFoundError: No module named 'audit_log'`）——agent 是把它写在
   `E:\agh-test3\node1_audit_setup.py`（worktree 根目录）而不是 `program-design/hooks/` 下面，
   用 `import audit_log` 裸 import 当然找不到（`audit_log.py` 在 `program-design/hooks/` 里，
   不在 Python 的 `sys.path` 默认搜索路径上）。agent 最终修正了这个路径问题（改成了正确的
   import 方式），但这个"钩子脚本该从哪里 import"本身是一个**没有写进任何协议/文档的隐性
   约定**（`boundary_gate.py` 的 `model_module` 上一轮刚补过一条"要在启动目录下可 import"
   的说明，但 `audit_log.py`/`dimensional_gate.py` 这类"agent 自己要写的小脚本"跟钩子脚本
   之间的 import 关系没有任何指引）。这是"02 走查预判清单"里"没有写过的通用约定"这一类
   问题的又一个实例，本轮先记下来，跟 4.1 那些报告呈现层问题分开，属于"协议/文档还没覆盖到、
   真实跑起来才会暴露"的下一批待办。
4. **同一份"数据源可用性检查"在 2025A 里出现了三次几乎重复的 shell 调用**（先失败一次
   `ambiance.Ambiance()` 写法，再改对，再又跑了一次类似调用）——不是 bug，是"没有一次做对"
   的痕迹，跟第 2 条是同一件事，合并记录，不单独算一条新问题。

  审批机制层面查一次（`packages/` 下的 approval 相关代码），**本轮没有查，不下结论**，只
