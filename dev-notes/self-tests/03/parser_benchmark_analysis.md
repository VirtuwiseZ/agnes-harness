## 1. 速度对比（同 5 篇，本机同一台机器，非 GPU 参与任何一家）

| 文件 | pypdf | pdfplumber | PyMuPDF4LLM | MinerU（basic，本地ONNX/CPU） |
|---|---|---|---|---|
| A-112（4.3MB） | 0.61s | 1.84s | 19.03s | 74.9s |
| A-182（1.3MB） | 1.12s | 2.79s | 9.51s | ~75s |
| B-127（2.6MB） | 2.44s | 4.86s | 6.21s | ~130s |
| B-765（4.6MB） | 2.70s | 6.38s | 19.60s | ~130s |
| B-796（4.8MB，111页） | 8.05s | 14.50s | 24.59s | 337s |
| **5 篇合计** | **~15s** | **~30s** | **~79s** | **~840s** |

- `pypdf`/`pdfplumber` 是**毫秒到秒级**，5 篇加起来比 MinerU 单篇（B-796）还快；
  `PyMuPDF4LLM` 稳定在 6–25 秒/篇，比 MinerU 快一个数量级以上（本次实测比"预计
  更快"的判断还保守——127 那篇只要 6.2s，因为它页数少、纯文本为主；796 那篇 111
  页才拖到 24.6s，说明它不是"跟页数线性死磕"，是纯 CPU 文本提取+版式推断，不是
  跑模型）。
- **MinerU 的 4 位数量级差距（15s vs 840s）全部来自"它跑了模型推理"这件事本身**，
  不是 I/O 或编码问题——这跟你观察到的"太慢"完全一致，且是结构性的：只要本机
  4GB 显存够不到 `standard`/`advanced` 档，`basic` 档这个速度就是它的上限，
  **不可能靠调参优化掉**，只能靠"少用/换工具"绕开。

## 2. 提取质量对比（同一套指标，5 篇汇总）

| 文件 | pypdf 字符数/公式/表格 | pdfplumber 字符数/表格 | PyMuPDF4LLM 字符数/公式/表格 | MinerU 字符数/公式/表格/图片 |
|---|---|---|---|---|
| A-112 | 57803 / 0 / 0 | 57742 / 0表 | 60412 / 0 / 110行 | **2545359 / 108latex+34行内公式 / 51行表格 / 20图** |
| A-182 | 49594 / 0 / 0 | 48925 / 2表 | 49732 / 0 / 58行 | **1007151 / 341latex+146行内公式 / 24行表格 / 15图** |
| B-127 | 33845 / 0 / 0 | 34254 / 8表 | 46217 / 0 / 74行 | **2478580 / 150latex+26行内公式 / 45行表格 / 22图** |
| B-765 | 89033 / 0 / 1行 | 85466 / 19表 | 89505 / 0 / 161行 | **4437476 / 555latex+174行内公式 / 67行表格 / 35图** |
| B-796 | 109229 / 12(误报) / 0 | 108899 / 12(误报) / 23表 | 112507 / 12(误报) / 53行 | **3928006 / 501latex+88行内公式 / 49行表格 / 18图** |

读法：
- **"公式"这一列才是关键分水岭**：`pypdf`/`pdfplumber`/`PyMuPDF4LLM` 三家合计的
  `latex_hits`（真正的 LaTeX 命令命中，不是普通反斜杠）几乎全部是 0（B-796 那篇
  各自命中 12 次，但人工核对过，是代码块里普通 `\\` 转义符被误计入，不是真的
  数学公式）；**MinerU 一家独占了从 108（A-112）到 555（B-765）不等的真 LaTeX
  公式命中**——这不是"多抠出几个字符"的差别，是**"有没有公式理解能力"的代差**：
  三家轻量工具看到公式区域只会按字面位置把字符抠出来（公式在 PDF 里通常是独立
  的数学字体/文本框，按阅读顺序抠出来大概率是乱序的散字符，或者整块被跳过，
  跟正文文字混在一起没有可解析的结构），MinerU 是专门训练过的模型把公式识别成
  标准的 LaTeX 串（`$...$`/`\\[...\\]`），对 AI 来说是"能不能理解这个公式在说
  什么"和"只是一堆乱字符"的差别。
- **"表格"这一列**：`pdfplumber` 在"有没有表格结构"这件事上其实比 `PyMuPDF4LLM`
  更勤快（它主动调 `find_tables()` 检测表格边框，B-765 检出 19 张表/526 个单元格、
  B-796 检出 23 张表——而 `PyMuPDF4LLM` 虽然把"表格"也转成了 markdown pipe 行，
  但它没有独立的"这是不是一张表格"检测环节，只能靠版式推断，112/182 那两篇
  `pdfplumber` 检出的表格反而比 `PyMuPDF4LLM` 的 pipe 行数"更少的表"还多——
  说明**表格检测能力 pdfplumber 略强，但两者都不如 MinerU 的"公式+表格"综合
  质量**，而且差距是"识别成结构化数据"vs"识别成大概像表格的文本行"这个层次，
  不是"谁多抠出几行"的层次）。
- **"图片"这一列只有 MinerU 有**（`inline_image_refs`/`base64_img_blobs` 全是它
  独有的指标，三家轻量工具本次实测全部是 0 张图——它们根本没有"把图抠出来"
  的能力，只能读文本层）。
- **字符数差距巨大但不代表"轻量工具漏了大量内容"**：`MinerU` 输出 2.5M 字符/篇
  vs `pypdf` 5.8 万字符/篇，差 40 倍左右——**这个数字大部分是 MinerU 把 20–35 张
  图片全部编码成 base64 内联进 markdown 造成的体积膨胀**（base64 编码本身会
  把一张几 KB 的 JPEG 膨胀成几十 KB 的字符串），不是真的"pypdf 漏读了 40 倍
  多的文字"——把 MinerU 输出里的 base64 图片 blob 剥掉之后，纯文本部分跟
  `pypdf`/`pdfplumber` 的字符量级其实接近（本次没逐一剥掉重算，因为"够不够用"
  已经能从上面公式/表格/图片三列单独判断出来，不需要再看字符数这个指标）。

## 3. 一个本轮才发现的真 bug（不是我的脚本错，是库本身的行为）

`pypdf` 和 `PyMuPDF`（`PyMuPDF4LLM` 底层）在 127/796 两篇上，直接 `open(..., "w",
encoding="utf-8").write(text)` 会抛
`'utf-8' codec can't encode character '\ud835'` —— 因为这两个库在某些数学字体
（Mathematical Fraktur 区段）下，提取出来的字符串里夹了**孤立的、无法配对成
合法 Unicode 字符的 UTF-16 半 surrogate**（`0xD835` 是"前半截"，后面本该跟一个
`0xDCxx` 后半截组成一个 4 字节字符，但库直接只给了前半截，缺了后半截，成了
非法的孤立 surrogate）。这不是"内容真的丢了"（我用 `errors="replace"` 兜底后
确认实际丢失字符数是 0，只是这些半截数学字母在最终文本里会变成 `?` 占位符），
是**编码层面的库实现缺陷**——**如果 SKILL 里把 `pypdf`/`PyMuPDF4LLM` 直接列为
可用工具而不提醒"输出字符串要先做 surrogate 清洗再落盘/喂给下游"，agent 第一次
用到这两篇这类文档时就会踩到一模一样的坑**，这一点要写进协议，不是可选项。
`pdfplumber` 本次没复现这个问题（它 5 篇全部 `ok`），但**没有证据表明它永远不会
踩到**，稳妥做法是三家统一要求"输出字符串在写入文件或传给下一个工具之前，先过
一遍 surrogate 清洗"，而不是只对某一家打补丁。

## 4. 结论：你的分层设想，微调后基本成立，但有一处要改

**成立的部分（跟你的直觉一致）**：
1. **速度分层完全正确且比"体量"直觉更悬殊**：`pypdf`（~15s/5篇）→
   `pdfplumber`（~30s）→ `PyMuPDF4LLM`（~79s）→ `MinerU`（~840s），是一个
   清晰的、逐级 2–3 倍、最后 MinerU 甩开前面三家 10 倍以上的序列，"分层调用"
   这个架构判断是对的。
2. **PyMuPDF4LLM 是"轻量档"里最接近 MinerU 的一个**：它比 `pypdf`/`pdfplumber`
   多出来的关键能力是**"把版式结构转成 markdown"（pipe 表格、段落、标题层级）**
   和"图片/文字分离"（虽然本次没实测出真的抠出图片文件，但它有 `page.get_pixmap`
   这类原生 API 可以显式调出来存图，只是 `to_markdown()` 这条主路径默认没做）
   ——也就是说，"比 pypdf/pdfplumber 更懂版式"这件事是实打实的，不只是"更
   慢一点"。

**需要修正你表述的一处**（这是本轮最重要的发现，比速度结论更重要）：

3. **"体量"这个说法容易让"公式提取"和"速度"两件事被混为一谈，建议拆开**：
   - **速度/依赖体量**这一维：`pypdf ≈ pdfplumber < PyMuPDF4LLM << MinerU`，
     跟你说的一致。
   - **能力**这一维，真实排序是：`pypdf < pdfplumber ≈ PyMuPDF4LLM << MinerU`
     （`pdfplumber` 和 `PyMuPDF4LLM` 在"公式理解"这件事上**并列垫底**——两家都
     完全不会把公式转成 LaTeX，这是"轻量抽取工具"这一档的**共同天花板**，不是
     某一家的短板；真正拉开代差的是最后一跳 `PyMuPDF4LLM → MinerU`，这一跳的
     差距是"从'把公式区域当普通文字抠'到'识别出这是公式并转成 LaTeX'"的
     **质变**，不是量变）。
   - 所以 SKILL 里写"分层"时，**"轻量档"（pypdf/pdfplumber/PyMuPDF4LLM 三家）
     和"重量档"（MinerU）之间的分层，本质是"要不要真正读懂公式/表格/图片"
     这个判断，不是"文档大不大"这个判断**——判断依据应该是**"这份文档里有没有
     公式/复杂表格/需要抠图的插图"**，而不是"文件大小/页数"。本次 5 篇范文恰好
     全部是"公式/表格密集"类型（IPhO 官方解答论文），所以 5 篇全部落在"需要
     重量档"这一侧；**但协议不能因为"这 5 篇都需要 MinerU"就写死成"物理题
     一律用 MinerU"**——如果以后某道物理题的数据源是一份纯文字的实验流程
     说明（没有公式、没有表格、没有图），按"文档类型判断"的分层规则，应该
     走 `pypdf`/`pdfplumber` 这一档就够了，不需要动用 MinerU。

## 5. 落到 SKILL 的分层规则（草案，尚未写入 SKILL，等你确认）

按上面结论，`physics-agent-governance` SKILL 里"文档解析"这一节建议这样分层：

- **Level 0 — 判断文档类型**（agent 自己判断，不用工具）："这份文档里有没有
  公式/复杂表格/需要抠图的插图"——没有 → Level 1；有 → Level 2。
- **Level 1 — 轻量纯文本/表格抽取**（`pypdf` 或 `pdfplumber`，视具体需求二选一：
  只要正文文字用 `pypdf`（更快、更轻）；需要独立检测/提取表格结构用
  `pdfplumber`（它有专门的 `find_tables()`，`pypdf` 没有））：毫秒到秒级，
  **零模型依赖**。
- **Level 1.5 — 轻量版式结构抽取**（`PyMuPDF4LLM`）：当文档"有版式结构
  （表格/标题层级）但不是公式密集"时用它，自动转成 markdown 骨架，比
  Level 1 更省事（不用自己拼表格），速度 6–25s/篇，**零模型依赖**（只是
  CPU 版式推断，不是神经网络）。
- **Level 2 — 重量级模型解析**（MinerU，仅在"文档确实是公式/表格/图片密集"
  时才动用）：分钟级，需要 ONNX 模型，是本机 4GB 显存环境下唯一能真正
  "读懂公式"的选项（`standard`/`advanced` 档本机跑不动，只能走远程+用户明确
  同意上传，这条隐私边界规则跟之前定好的一致，不因本次分析改变）。
- **所有层级的输出，在落盘/传给下游之前，统一过一遍"孤立 surrogate 清洗"**
  （§3 那个 bug，不是只针对某一层的补丁）。

**你问的"放弃 MinerU、从项目 skill 里删去以免用户端 AGH 调用 mineru 出问题"
这件事**：本次实测数据**支持"MinerU 是重量档、默认不该被随意调用"这个判断，
但不支持"完全放弃"**——因为 5 篇范文全部是"公式密集"类型，Level 2 这一层
目前只有 MinerU 一家实测过、且是唯一在"公式理解"这个能力上真正跨过硬门槛
的工具（Level 1/1.5 三家全部实测确认不具备这个能力）。所以建议是：
1. **默认路径/自动调用规则里，把 MinerU 移出"Level 1 会碰到的默认候选"**，
   只在"文档被判断为公式/表格/图片密集"这个明确条件下才走 Level 2 显式
   调用它——这直接实现了你说的"以免用户端 AGH 自动/无脑调用 mineru 发生
   问题"。
2. **不把 MinerU 从 SKILL 里完全删掉**，而是**降级为"Level 2 专属、需要明确
   触发条件才启用"的条目**（跟"远程解析需要用户明确同意上传"是同一性质的
   显式门槛，不是默认路径），保留开发分支里已经装好的环境不用回滚
   （你说的"开发分支里可以留着"跟这个处理完全一致——环境层面保留，只是
   协议层面把它从"默认/自动"降级为"条件触发"）。

**这个降级方案 vs 你原始提议的"从 skill 里删去"，区别只有一点：删去 =
  以后某道公式密集的物理题来了，agent 手里没有任何已验证的重量级解析
  工具可用，会被迫每次临时重新评估/安装；降级 = 保留一个已经验证过、
  装好的、只在明确触发时才动用的重武器。基于"5 篇全部需要重武器且重武器
  只有 MinerU 一家实测可用"这个实测结论，我推荐"降级"而不是"删去"，但
  这个决定（保留 or 彻底删除）是你的，等你拍板，本次不动手改 SKILL。**
