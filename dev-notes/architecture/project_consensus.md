# 项目共识与架构设计规范 (Project Consensus & Architecture Spec)

## 0. 顶层架构铁律：非侵入式扩展原则 (Zero-Intrusion Baseline)
- **核心约束**：本项目基于 Agnes Harness (AGH) 基座构建，**严禁对 AGH 宿主仓库的源码核心（如 `packages/*`、内置系统提示词、`AGENTS.md` 等基础定义）进行任何侵入性修改或覆盖**，以保障项目对任意标准 AGH 实例的适用性（泛用性）。
- **落地准则**：所有项目的架构规范、知识库扩展、防线钩子，必须通过 AGH 官方支持的非侵入式标准扩展路线实现：
  1. **Skill 隔离封装**：项目宪法、物理协议及知识库路由规则，仅能封装在标准目录 `.agh/skills/` 下（如 `.agh/skills/physics-agent-governance/SKILL.md`）。
  2. **自有数据隔离**：项目的物理参数、审计状态机记录（如 `problem_state.json`）及方法模板，必须全部沉淀在项目自有的 `program-design/` 目录下，通过 Skill 协议驱动调用。
  3. **宿主兼容性**：任何开发操作如果必须在 AGH 宿主环境中运行确定性脚本（如量纲校验、边界自检），应以独立 Python 脚本的形式通过工作区文件系统调用，而不修改宿主代码底层机制。
- **工具接入优先原则（避免重复造轮子）**：
  - 编写任何确定性校验钩子前，**先检索是否存在成熟的开源/行业标准库**（如 `SymPy`、`Pint`、`NumPy`、`scipy`）可直接满足该钩子的核心判定逻辑；**存在则直接接入，不手写重复实现**。
  - 只有当标准库未覆盖、且属于本项目特有协议（例如“变量量纲必须被 AI 显式声明并沉淀进状态机”）的部分，才允许编写**薄胶水层**，且须在脚本头部注释中**显式声明**“底层依赖 X 库，本脚本仅实现 Y 协议胶水，非独立引擎”。
  - 每个钩子目录必须维护一份 `requirements.txt`，声明全部第三方依赖边界。
  - 该原则本身即对应赛事“调用外部能力”条款：项目展示的能力是**“判断何时该用第三方成熟工具、并正确接入”**，而非闭门造车。

## 1. 项目基础信息与赛事合规对齐 (Project Scope & Compliance)
- **项目定位**：基于 Agnes Harness (AGH) 构建的轻量级、可执行、可验证的物理科研 Agent 原型，重点体现确定性工程防线、多步连续执行能力与结论防伪溯源。
- **题目选型与职责划分**：
  - **主 Demo (2023 空间跳伞 GM-A-131)**：跑通全链路执行流。涵盖任务规约、知识库路由、调用外部大气数据 API、分阶段 ODE 数值求解、与 Baumgartner 39 km 实测对照验证，并作为跨音速阻力突变导致的数值异常/假设退火的核心演示。
  - **副题边界用例 (2010 抛石机 GM-B-210)**：复用下落/能量模型模板，重点验证极端退化边界条件（如配重提升高度 $h \to 0$、绳长 $r_3 \to 0$ 时的动能极限响应）。
  - **未来展望 (2020 离子推进 GM-A-340)**：仅在报告产物末尾作为跨星际多阶段轨道转移的知识库迁移性展望，不纳入主执行链路。
- **赛事硬性指标映射**：
  1. 连续执行步骤 $\ge 3$（实际规划为 4 节点执行链）；
  2. 调用真实外部能力（科学大气数据库/API、科学计算库）；
  3. 独立客观对照验证（与实测数据量化比对误差，杜绝模型自验自证）；
  4. 完整复现与记录至少一次异常/边界/退火处理过程；
  5. 演示呈现与测试结果严格一致。

## 2. Harness 确定性防线与上下文治理机制 (Governance & State Management)
- **三道确定性防线（由 Harness/独立 Python 钩子强制执行，严禁仅依靠 LLM Prompt 自律）**：
  1. **量纲与符号门禁 (Dimensional Gate)**：输出物理公式后，必须由确定性脚本调用 `Pint` 或 `SymPy` 验证量纲齐次性，失败则硬性阻断后续数值计算。
  2. **边界物理自检门禁 (Boundary Gate)**：设计物理极值检验用例（极限质量、零阻力、零高度等），自检通过方可流转至报告节点。
  3. **配额管理与退火回滚 (Quota & Annealing Rollback)**：下游数值求解与代码纠错设定硬性尝试配额（$N \le 3$）。连续发散或超限时，强制触发退火策略，状态机回滚至“物理假设层 (Hypothesis Layer)”重新评估边界与参数，禁止模型在下游代码中私自修补物理假设。
- **上下文管理与唯一事实源**：
  - 杜绝整段历史对话的无序滚动轮递；
  - 核心状态由根目录/工作区 `problem_state.json` 统一纳管（Schema 包含：任务目标、当前假设、物理量纲表、工具调用历史、数值产物、审计日志、异常状态与当前阶段）；
  - 外部能力（API、外部数据、仿真运行）调用必须实时写入结构化审计记录（含 source、timestamp、args、hash/artifact_id）；
  - 最终结论采用“引用约束”：报告中的核心数字与结论必须携带溯源标记，直接锚定至状态机已验证的数据产物。

## 3. 知识库解耦设计 (Knowledge Base: Skill + JSON)
- **资产解耦原则**：将物理求解论沉淀为可复用资产，实现同类问题泛化迁移，杜绝单一题目的定制硬编码。
- **方法论层 (Skill 协议与模板库)**：
  - 抽象通用的物理求解范式（如 `atmosphere-drag-ode` 气动阻力下降求解流、`boundary-verification` 极值判定流、`parameter-sensitivity` 敏感度分析流）。
- **题域参数层 (JSON 配置)**：
  - 独立管理具体物理参数、安全阈值与真实基准数据（如 `space_diving_params.json` 包含总质量 190 kg、NASA 人体过载极限 $\pm 5\text{G}$、Baumgartner 39 km 真实高度-速度对照表）。
- **执行逻辑**：
  - Agent 在任务规划后，通过 Skill 协议检索匹配通用方法模板，读取对应参数 JSON 实例化执行，实现“结构与参数分离”。
- **数据源解耦原则（新增，配套“泛用性”要求）**：
  - 数值模型代码（如 ODE 求解器）**不得硬编码任何具体外部数据源**（不得写死“调用 NRLMSIS”这类绑定），只应接收一份结构化数据输入（如 `T(z)`/`ρ(z)` 数组）。
  - 该数据输入由一个**新增的“数据源分析”环节**在 Demo 运行时动态产出：Agent 针对当前物理题的具体条件（大气环境、高度范围、精度需求、公开数据可得性），**即时联网检索**并判断“该题应调用什么数据源、以什么方式接入（API/公开数值表/解析公式近似）”，同时把判断理由与结果写入 `problem_state.json` 的审计日志。
  - 该判断属于“决策执行”而非“写死的配置”，是演示 Agent 连续执行能力的关键一环；独立对照验证基准（如 Baumgartner 实测数据）同样应通过此机制选定，不得写死。
  - 方法论模板本身描述的是“如何调用一份 T(z)/ρ(z) 数据”，不绑定具体数据源名称；数据源名称仅出现在运行时产出的审计记录里，不出现在模板或代码里。

 ## 4. 四阶段执行流水线与只读前端设计 (Pipeline & Visualizer)
- **流水线四个连续执行节点**：
  - **Node 1: 任务理解与规约 (Task Specification)**：解析题干需求，提取待求物理量与安全约束，初始化 `problem_state.json`。
  - **Node 1.5: 数据源分析 (Data-Source Routing，新增)**：Agent 针对当前题目条件即时联网检索并判断“建模需要哪份外部数据、用什么方式接入”，以及“验证对照基准应引用哪份公开数据”；判断结论 + 理由写入审计日志，数据源名称不进入方法论模板或代码本体。
  - **Node 2a: 知识路由 (Knowledge Routing)**：通过 Skill 协议路由至对应物理方法模板，装载参数 JSON，形成可审计的调用记录。
  - **Node 2b: 建模求解与验证 (Modeling, Execution & Verification)**：执行量纲检查、按 Node 1.5 结论拉取/解析外部数据、运行数值积分（代码层不绑定具体数据源，仅接收结构化输入数组）、比对 Node 1.5 选定基准的实测对照组；包含边界测试与配额退火机制。
  - **Node 3: 严谨报告生成 (Audited Report Synthesis)**：汇总已验证指标，生成附带量纲通过标记与溯源引用的结论报告。
  - **Node 4: 流程树可视化渲染 (Trace Visualizer Render)**：调用只读导出脚本，将完整 transcript 及状态流转导出为自包含、纯静态的单文件 `HTML`。
- **前端可视化铁律**：
  - 纯静态单文件 HTML，双击即开，现场零依赖运行；
  - 前端对 Harness 导出数据保持绝对只读，禁止 Agent 回写或篡改历史失败/退火轨迹，确保真实审计与合规演示。

## 5. 更新说明 / commit message / 收尾 summary 写作规范 (Documentation & Summary Style)
本节规范的是“写给下一个读这份说明的人”的内容风格（commit message、dev-notes 里的更新记录、任务收尾 summary、给协作者的分支说明文档），适用对象是**没参与当次会话/开发的人**，不是对话里下指令的开发者本人。

- **不用对话口吻**：不写“我完成了 xx，还有 xx 需要你来审核”“等你点头”“请你确认”这类把读者当成对话对象、要求对方动作的句子。Summary/说明是记录，不是交接喊话。如果确实还有未完成事项，写成客观状态描述（例如“此功能尚未做 X 的验证”），而不是要求读者做什么。
- **不用只有当事人才懂的指代**：不写“步骤 C”“待办 2”“上面第 3 条”“§7 末段”这类需要回头翻上文才能解码的编号/代词。每条改动要写清**这件事本身是什么**（涉及哪些文件、哪个功能、哪个图类型），让第一次读这份说明的人不依赖前文也能看懂。
- **让读者自行看懂更新内容**：每条改动写清“做了什么 + 为什么 + 影响范围”（改了哪些文件/函数/字段，是新增能力还是修复，跟哪些既有行为不冲突或会受影响），不依赖“你应该还记得”的隐含前提。
- **事实与判断分开写**：客观事实（改了哪几个文件、验证过什么、结果是什么）和主观判断/建议（“后续可以…”，“这条边界还没覆盖到，风险是…”）分开标注，不把“建议”混在事实叙述里让人误以为已经验证过。
- **不虚报完成**：没跑通的验证、没覆盖的边界、没测过的场景，如实写“未验证 / 未覆盖 / 尚未测试”，不写“已完成”；不能为了收尾好看把没做的事写进去。
- **可追溯**：涉及代码改动时，写明文件路径（必要时带函数名/字段名），读者能直接跳过去核对，不需要另行搜索。
- **语言与项目一致**：本项目文档/共识默认中文，专有名词（如 `plotly`、`interactive_live`、`y_range_pin`、具体 `kind` 名）保留原文，不硬译。
- **克制长度，不重复啰嗦**：同一事实不在多处重复表述；该写的都写清楚，但不过度展开背景铺垫。
- **git 状态如实陈述，不用请求语气**：例如写“已提交到 `physics-agent` 分支，尚未推送到远程”（事实），不写“等你同意再 push”（请求）；如果是自己发起的、需要他人决策的事项，单独列一节明确写“以下为待你决策的事项”，把它跟“已完成事实”分开，不混写。
