## 第 1 部分：对 Harness 架构特点、优势的结合情况审视

### 1.1 上下文管理与提示词优化：全程规划文档是否缺失？

**开发者原始想法**（大意）：AGH 官方有自己的上下文梳理和传递机制，但本项目对「单个
物理问题的全流程」目前是否有明确的上下文管理设计？具体关切是：如何避免 AI 在长任务
执行过程中"不小心绕进一个子问题"（即偏离主线），如何管理由此产生的文件（避免散落
各处）。理想形态是：接到任务后先草拟一份总体规划并落成 md 文档作为锚点；执行过程中的
每个小步骤都写进同一份规划文档的对应板块（逐条追加），或者单独另起 md。这样到写报告
时，这份规划文档本身就成了"全流程记录"，可以直接用来总结。

**现状核查（引用实际文件证据）**

1. `program-design/problem_state_schema.md`（已读全文）已定义 `problem_state.json`
   为「单次运行的唯一事实源」，规定了严格的字段所有权（`task`/`stage`/`quota`/
   `hypothesis_layer`/`dimensional_table`/`knowledge_routing`/`data_source_decision`/
   `internal_prior`/`numerical_artifacts`/`audit_logs`/`anomalies`/`verification`/
   `report` 各自只有一个合法写入方，跨节点只能追加 `audit_logs`/`anomalies`，不能
   改写早先节点的字段的规则）。这是**节点间**交接的结构化防偏离机制。
2. 同一 schema 文件还规定 `report_<task-slug>.md`（Markdown 研究叙述正文，非 JSON
   字段）由各节点在边界处追加、Node 4 只读。这是"报告即逐步追加"的既有雏形。
3. `.agh/skills/physics-agent-governance/SKILL.md`（245 行，已全文核查）里**没有**
   任何"接到任务先写一份总体规划 md、之后每一步都要回头对照这份规划来防偏离"的
   规定。全文件检索"规划""偏离""主线""roadmap"等关键词，唯一命中的"deviation"是
   `interactive_live` 图那种"参考值偏差读数"（`verify_reference_*` 字段），与任务
   主线偏离无关——即这是一个关键词巧合命中，不是本条关切的对象。
4. 本次会话本身（非仓库内既有文件）已经暴露过这类风险：本轮"深挖 FEM 参考文件 +
   落地 3 条 interactive_live 增强"这条线，规划散落在 4 份不同文档
   （`dev-notes/interactive_figure_design.md` §7、`dev-notes/self-tests/03/
   charting_generic_architecture.md` §11、`dev-notes/self-tests/03/figures_interactive_
   test/reference_fem_realtime_simulation_notes.md` §3/§4、SKILL.md §7）里，且这 4 份
   都写完之后才在 `dev-notes/development_backlog_review_2026-10-09.md` 里做了一次"
   还有哪些没做完"的总回顾——这是**事后**整理的待办清单，不是**事前**就立好、执行
   过程中持续对照更新的那份规划本身。

**缺口分析**

- 现有 `problem_state.json` 字段所有权机制管的是"节点之间不允许乱改对方字段"
  （结构完整性层面），不是"当前这一步有没有偏离最初接到的任务目标"（意图/主线层面）。
  两者是不同问题：即便所有字段都严格按规定写入，`stage` 依然可以按顺序正常推进，
  但 `task` 字段里"这次到底要交付什么"这件事本身不会在每一步被重新拿出来对照。
- `report_<task-slug>.md` 是"边算边写的报告正文"，定位是结果叙述，不是过程规划；
  把"这一步为什么这么做、有没有绕偏"的判断写进报告正文里反而会让最终报告本身
  掺进执行期的一次性权衡记录，跟"报告是给最终读者看的成品"定位冲突。
- 结论：**"规划文档"这一层，目前项目里没有对应物**。这是本次审视发现的第一个明确
  缺口，不是文档没写好的问题，是这一功能本身尚未设计出来。

**建议方案（新增 `program-design/runtime/planning_<task-slug>.md`）**

1. 触发时机：Node 1 写完 `problem_state.json` 的 `task` 字段之后、进入 Node 1.5/2a
   之前，必须先生成一份 `program-design/runtime/planning_<task-slug>.md`，内容包含：
   ① 任务目标（跟 `task` 字段对齐，用自己的话重述一遍，作为后续每一步的"锚点"）；
   ② 预期交付物清单（报告、验证结果、图表——哪些是必须的，哪些是可选的，预先写清）；
   ③ 本次计划调用哪些知识库模板/数据源/图表类型（预判，非承诺，后续实际偏离预判时
   要在这里标注偏离原因，不是悄悄改掉）。
2. 每一步（Node 1.5 / 2a / 2b / 2.7 / 3 / 4）进入前先读这份规划文档，退出前必须向
   文档追加一个「步骤小结」小节：本步做了什么、跟最初预判相比哪里一致/哪里偏离、
   偏离原因、下一步预计要做什么。这是一个**追加式**的板块（跟 `audit_logs` 的
   append-only 原则同源，避免后面某一步回头改写前面某一步的小结——跟
   `problem_state.json` 的"节点不许改写早先节点字段"是同一套纪律，只是对象从
   JSON 字段扩展到了规划文档里的记录段落）。
3. Node 3 写报告时，允许直接引用这份规划文档里各步骤小结的内容作为"过程回顾"
   章节素材（区别于 `report_<task-slug>.md` 本身——那是结果叙述，规划文档是过程
   记录，两者分开，报告里可以两者都用但标注来源不同）。
4. 落进 schema 的方式：`problem_state.json` 新增一个可选顶层字段
   `planning_doc`（值是一个相对路径字符串，指向该 md 文件；`task` 字段写入的同一
   时机创建，`stage` 推进到 `done` 之前该字段必须非空，否则按"缺失必要交付物"
   硬报错，跟"figures 字段可以为空但 planning_doc 不可以为空的对称设计"一致）。
   新增字段所有权规则：只有当前 `stage` 对应的节点可以向它追加内容，跟 `audit_logs`
   一样是追加式，不允许改写已写入的历史段落。

**实施代价与风险提示**

- 改动面：`problem_state_schema.md` 新增 1 个字段 + 1 条所有权规则（约 20–30 行）；
  `SKILL.md` 的 Node 1 章节加一段"创建规划文档"的操作说明（约 10–15 行）；
  `trace_visualizer.py` 需新增"把这份 md 也内联进最终 HTML 报告"的内联逻辑
  （跟现有 `report_<task-slug>.md` 的内联逻辑并列，约 20–30 行）。
- 风险：规划文档如果写得过细（比如把每个假设的具体数值都预先写死），跟
  `hypothesis_layer` 的"退火回滚"机制会冲突——假设被退火改掉之后，规划文档里
  预先写的那份数值预测会过时。建议规划文档**只记录"预判方向/预判要用的方法"，
  不预先写死具体数值结论**，数值结论以 `verification`/`hypothesis_layer` 字段为
  准，规划文档只做"过程是否偏离预设方法路径"的对齐检查，不碰数值正确性判断
  （跟现有 `numerical_artifacts` 字段"零判断渲染层"的设计原则同源，这里延伸成
  "规划文档也是判断之外的记录层"）。
- 该条改动是**新增功能**，不修改任何现有字段语义，理论上向后兼容（老 trace 没有
  `planning_doc` 字段不影响回放），但 `trace_visualizer.py` 需要能处理"该字段缺失
  但 stage 已经是 done"的旧数据情况（显示"此任务无规划文档"占位，而不是报错）。

**开放问题（本次未决）**

- 规划文档的粒度：是"每个 pipeline 节点一个板块"还是"每个 Node 2b 的每次代码
  重试（quota 计数内）也算一个可记录的小步骤"？前者改动小但颗粒度粗，后者更贴近
  "AI 不小心绕进子问题"这个原始关切（子问题大概率发生在 2b 的反复调试阶段），
  但会让规划文档在小任务里也变长。倾向于先按节点级实现，quota 内重试只在
  `audit_logs` 里记录（现状已够），观察是否需要细化到"每次重试都写一条规划
  文档条目"。
- 是否要一份"规划文档模板"（`program-design/knowledge/` 下加一个 `planning_template.
  md`），供 Agent 照抄结构而不是每次都即兴写——倾向于要，模板本身就是把"这一层
  到底记什么"这件事固化下来，避免不同 Agent 会话对"规划文档该写多细"理解不一致。
- **本轮新增顾虑（未决）**：规划文档跟 AGH 宿主自身记录 Agent 每一轮工具调用的
  机制（`program-design/hooks/trace_capture.cjs` + `trace_visualizer.py`，即 Node 4
  用的那套）会不会功能重叠？核查结论：`trace_capture.cjs` 实际只产出三种事件类型
  （已核实其源码 `convertLine` 函数，见 `program-design/hooks/trace_capture.cjs` 第
  119-154 行）——`tool/call`（工具名 + 参数原样记录）、`tool/result`（工具返回内容
  + 是否失败标记）、以及其它所有事件被归一成 `session/start` 占位（只记录"有这样一个
  事件类型"，不记录具体语义）。也就是说这套 trace 记的是"实际发生了什么操作、每个
  操作输入了什么参数、拿到了什么结果"，是一个**纯操作日志**（往回看，"发生了什么事"）；
  它**不**记录"在决定执行这个操作之前，Agent 预期的结果是什么、为什么预期是这样、
  如果实际结果跟预期不一致该走哪条分支"——这一层**前瞻性意图/计划演变**信息，
  `trace_capture.cjs` 的三种事件类型里没有任何一种对应得上（`tool/call` 只记参数，不
  记"为什么是这个参数"；`tool/result` 只记结果对不对，不记"结果跟事先的预期比差多
  少"）。所以规划文档（1.1 原方案）如果定位成"每个节点开工前先写下预期/假设，跟实际
  操作日志对照看有没有偏离"，跟 trace 是**互补而非重叠**：trace 是"发生了什么"（操
  作层），规划文档是"本打算发生什么"（意图层），后者目前没有任何其他机制在记录，不建
  的话确实缺。但这一点目前只是基于 `trace_capture.cjs` 源码的推断（它确实只记操作、不
  记意图），还没有实际拿一道题的完整 trace 输出跟一份同时段的规划文档对照过、验证
  "意图层"信息在真实跑题时确实无法从 trace 反推出来——这个对照验证本身也还没做，属于
  本条开放问题的实际检验步骤，不是本次能下结论的地方。

### 1.2 AGH 工具/技能注册表：泛用性文件是否按"通用文件 vs 特定任务临时文件"分开整理？

**开发者原始想法**（大意）：本项目的开发、测试过程中沉淀下来的、有泛用性的文件（
Python 程序、算法、第三方数据库/工具、网页/可视化设计与代码），有没有按照"面向所有
物理问题预备的通用文件"与"为某道特定物理问题临时生成、用完就结束的文件库"这两类
分开整理？

**现状核查（引用实际文件证据）**

1. **通用文件那一侧**：`program-design/hooks/`（`audit_log.py`、`boundary_gate.py`、
   `dimensional_gate.py`、`make_report_figures.py`、`ode_model.py`、`trace_capture.cjs`、
   `trace_visualizer.py`）—— 这是"面向所有物理问题预备"的确定性脚本层，职责边界清晰
   （钩子脚本本身不绑定具体题号，靠 `problem_state.json` 喂入数据），且每个脚本都有
   独立的 `requirements.txt` 依赖边界声明，跟共识备忘录 §0 的"非侵入式扩展 + 薄胶水层"
   原则一致。`program-design/knowledge/`（`atmosphere-drag-ode.md`、`boundary-
   verification.md`、`data-source-routing.md`、`parameter-sensitivity.md` + 一个
   `space_diving/` 子目录）—— 这是方法论模板层，同样设计成"问题无关，描述怎么判断/怎么
   调数据，不写死具体数据源名字"（`data-source-routing.md` §1 开头明确写"This
   template is deliberately problem-agnostic"）。`program-design/runtime/problem_state_
   template.json` / `task_params_template.json` 是空白骨架模板，也是通用的。
2. **特定任务临时文件那一侧，混着放在了不该放的地方**：
   - `dev-notes/第三方数据/`（字面意思就叫"第三方数据"）目前**同时**装着两层不同性质的
     内容：一层是真正的第三方公开数据集本身（`gistemp_global_anomaly_1880-2026.csv`、
     `nasa_exoplanets_mass_radius.csv`、`nist_codata2022_constants.txt`、
     `sidc_sunspot_monthly_1749-2026.csv`、`hydrogen_emission_lines.csv` + 一份
     `heatmap推荐数据源.md` 说明哪类题目适合用哪个数据源）—— 这部分是**可复用**的，
     任何一道未来要用到全球气温异常/系外行星质量半径/CODATA 常数/太阳黑子/氢发射线
     的题目都可以直接用，不是某个特定任务用完就废弃的；另一层是 `dev-notes/第三方
     数据/figtest/` 下的一批一次性的调试/验证脚本（`debug_codata.py` ~ `debug_codata13.py`
     共 14 个、`check_*.py` 若干、`probe_*.py`、`commit_*.py`）—— 这些是当时逐行排错用的
     探索脚本，本身没有复用价值，之前已经在 commit 里明确标注过"一次性调试产物，不进
     git 历史，保留在 figtest/ 目录里供随时重查"，是**开发留痕**，不是数据资产。
     两层东西目前挤在同一个 `dev-notes/第三方数据/` 目录树下，没有按"可复用数据源"
     vs "一次性调试脚本"做过任何目录级区分。
   - `dev-notes/self-tests/02/`、`dev-notes/self-tests/03/` 里还有更大体量的同款情况
     （`02/` 下约 20 个 `probe_*.py`/`repro_*.py` 探针脚本 + 若干一次性 diff/中间产物；
     `03/` 下一次性验证脚本 + 各 kind 的合成/回归测试数据目录 `figures_2025A_sasando/`、
     `figures_edge_cases/`、`figures_interactive_test/` 等），跟 `第三方数据/figtest/` 是
     同一种"任务执行过程中随手写的探索代码"性质，体量更大（几十个文件），目前也全部
     挂在 `dev-notes/self-tests/` 下没有跟真正可复用的数据/模板做任何目录分离。
   - `dev-notes/self-tests/03/figures_interactive_test/` 里混着两种性质的文件：`build_
     sasando_interactive_live.py` / `build_sasando_interactive_live_enhanced.py` / `check_
     enhanced_frag.cjs` / `problem_state_2025A_sasando_with_interactive_live_enhanced.json`
     是**演示 + 验证脚本 + 示例输入**（有复用价值，能用来快速验证"这个新 figure kind
     有没有被后续改动弄坏"），`sasando_live_out/` / `sasando_live_enhanced_out/` 是
     **一次性跑出来的成品 HTML**（展示用的最终产物，不是可复用资产），目前也没区分开。
3. `.agh/skills/` 下**只有 1 个** skill（`physics-agent-governance/SKILL.md`），没建过
   第二个；`mineru_integration_assessment.md`（`dev-notes/architecture/` 下）里评估过"要不要
   接 MinerU 官方 Skill"，结论是走"在项目自己的 governance SKILL 里加判断规则 + 在
   `data-source-routing.md` 里加文档型数据源这一层"，**不**额外注册一个独立的 MinerU skill
   文件—— 也就是说 skill 层面目前是"一个大而全的 governance skill"形态，没有按能力拆分成
   多个小 skill 再往注册表里注册的动作（AGH 的 skill 机制本身是支持多 skill 并存的，
   本项目选择了单 skill 路线，这是当前事实，不等于"用错"，但跟"是否利用了注册表按
   能力分列"这个问题直接相关——答案是：没有按能力分列，是一个 skill 包办全部治理规则）。
4. **`make_report_figures.py` 与 `trace_visualizer.py` 之间的关系没有形成独立的、可被
   其他题目直接引用的"图表通用工具包"**：这两个脚本目前直接硬编码在 `program-design/
   hooks/` 里，靠 `problem_state.json` 的 `numerical_artifacts.figures` 字段驱动，
   任何一道物理题要画图都必须走"先填这个字段、再跑这个脚本"的固定路径，没有抽象出
   "跟物理题无关的、只依赖数据数组的通用绘图入口"（比如一个 `chart(data, kind, opts)`
   风格的 API），跟"面向所有物理问题预备的通用文件"这一定位其实是一致的（不需要更通用，
   物理题之外的场景不在本项目范围内），但**没有做"哪些 kind 是给哪类题型的通用解法"
   这种归类说明**—— 目前 `charting_generic_architecture.md` 里是按 kind 维度写的
   （curve/scatter/.../interactive/interactive_live 各自一节），没有按"题型→推荐 kind"
   反查的索引，Agent 拿到一道新题要判断"该用哪个 kind"时，要通读 kind 说明而不是
   查一张"什么题该配什么 kind"的速查表。

**缺口分析**

- "通用"与"任务专属"这条线，在 `program-design/` 目录里是清晰的（钩子脚本、知识模板、
  状态模板全部是通用层），但一旦进入 `dev-notes/`，这条线就完全混在一起了：可复用的
  第三方数据集（`第三方数据/*.csv`/`*.txt`/`heatmap推荐数据源.md`）跟一次性调试脚本（`第三方
  数据/figtest/debug_codata*.py`、`check_*.py`、`probe_*.py`、`commit_*.py`）挂在同一棵目录
  树下，且 `self-tests/02`、`self-tests/03` 下体量更大、性质更杂（测试数据目录、验证脚本、
  演示产物、一次性 trace 样本混在一起），没有一层目录结构帮读者（或未来的 Agent 会话）
  判断"这个文件是值得留作下次直接用的，还是这次排错顺手写的、不用管它"。
- 这不是"目录命名不规范"的小问题，是一个"资产分类"的架构决策缺失：项目目前没有一个
  明确的目录约定写下来，规定"哪一层是通用可复用资产（数据/模板/脚本）、哪一层是执行
  留痕（一次性调试/验证产物），两者物理上放在哪、各自的生命周期规则是什么（比如留痕
  层允许被定期清理，通用层不允许）"。目前这条约定是**隐含在**各次 commit message
  里的（如 `0b5e9086` 那条 commit 里"一次性调试产物按约定不提交，保留在 figtest/ 目录
  里供随时重查，不进 git 历史"），但这条约定本身没有被写成一份固定的目录规范文档，
  意味着换一个 Agent 会话来做同样的任务，没有地方可以查到"debug_*.py 这类文件该放在
  哪、该不该进 git"，只能靠读历史 commit 自己猜。
- skill 层面没有按能力拆分（1 个大 skill vs 多个小 skill）不是一个错误，是一个已经
  做出过的架构选择（`mineru_integration_assessment.md` 里明确评估过并选择了不单独注册
  MinerU skill 的方案），但这条"选择"本身**没有写进共识备忘录**，只写在评估文档里，
  意味着以后如果想加第二个能力（比如单独拆一个"数据获取"skill、或者拆一个"报告排版"
  skill），没有一份说清楚"什么时候该拆、拆的判断标准是什么"的既定规则，只能到时候
  重新评估一次。

**建议方案**

1. 新增一份 `dev-notes/README-资产分类规范.md`（或直接写进 `project_consensus.md` 的
   一个新章节，取决于"这是架构共识还是操作规范"的判断——倾向前者，因为这是全项目共
   享的目录约定，不是某一个功能模块的设计文档），明确三层：
   - **通用资产层**（`program-design/` 全部 + `dev-notes/第三方数据/` 顶层的
     `*.csv`/`*.txt`/`heatmap推荐数据源.md` 等纯数据文件）：面向所有未来物理题预置，
     长期保留，不允许删除，只能新增。
   - **验证/演示层**（`dev-notes/self-tests/*/` 下真正可复用的部分：合成测试 state
     文件、边界用例数据、演示 HTML、验证脚本如 `check_enhanced_frag.cjs`）：跟某一次
     特定功能的验收直接相关，保留用于日后回归验证该功能有没有被改坏，生命周期是"跟着
     它验证的那个功能存在多久就留多久"，该功能被合并进主线后这份验证产物依然有价值，
     不是用完即弃。
   - **执行留痕层**（`dev-notes/self-tests/02/`、`03/` 下的 `probe_*.py`/`debug_*.py`/
     `check_*.py`（一次性排错用的，不是验证脚本）/`commit_*.py`/`*_out/` 中间产物）：
     只保留在工作区磁盘供当时参与排查的人回头重查，不进 git 历史，允许定期清理，清理
     前只需保证"有没有对应的一次性 bug 还没修完"（如果修完了，这批文件就该删掉腾出
     视野，防止下次排错时误以为还有人在用它们）。
2. 跟 SKILL.md 的"当前问题只能用哪些输入"（已核实，见 `SKILL.md` 里那条"The only
   inputs you may use for the current problem are: ..."）对齐：这一条目前列的是
   `program-design/knowledge/`、`program-design/hooks/` 等通用层路径，没有明确写
   "**不得**直接读 `dev-notes/第三方数据/figtest/` 下的一次性调试脚本作为数据源或
   方法参考"—— 建议在 SKILL.md 里明确把"执行留痕层"从允许的输入来源里排除掉，
   防止未来某次 Agent 会话在找不到现成模板时，去翻一次性的调试脚本当临时参考。
3. 关于"题型→推荐 kind"的反查索引：在 `dev-notes/self-tests/03/charting_generic_
   architecture.md`（或独立一份 `program-design/knowledge/figure-kind-selection.md`）里
   加一张速查表，按题型（单值最优化/曲线族对比/参数敏感性扫描/2D 参数面/分布检验/
   交互式探索）列出"这类题通常配哪种 kind、为什么"，把目前散落在各 kind 说明段落里
   的判断标准收成一张可以直接查的表，降低 Agent 每次从头读全部 kind 说明的认知负担。

**实施代价与风险提示**

- 第 1 条（资产分类规范）主要是**目录/命名约定 + 一份文档**，不需要改任何代码，实施

  东西如果当初是被当作"第三方数据资产"落到 `dev-notes/第三方数据/` 的，属于通用层，

- 第 3 条（kind 选型速查表）是纯新增一份轻量文档，无风险。

**开放问题**

- 是否要为"验证/演示层"单独建一个跟 `dev-notes/self-tests/` 平级的目录（比如
  `dev-notes/regression-assets/`），还是继续放在 `self-tests/` 下但靠新规范文档区分

- 是否要按"数据/代码/文档"再切一次正交的维度（比如 `heatmap推荐数据源.md` 是文档，
  但它描述的内容指向的是数据；`check_enhanced_frag.cjs` 是代码，但它验证的是某个具体
  功能——按"是什么东西"分类 vs 按"服务什么目的"分类，两种维度会给出不同的目录结构）。

**已决（本轮，开发者拍板，替代上面两条未决问题）**

1. "验证/演示层"**物理挪到独立顶层目录**（如 `dev-notes/regression-assets/`），不再跟

2. 三层分类**不再按"数据/代码/文档"加第二正交维度**——维持按"服务什么目的/生命周期"

3. 新增一条："题型→推荐 figure kind"速查表**不另开新文件**，直接加进现有的

   度讲设计，把"什么题该配什么 kind"的反查表加在同一份文档里，比单开一份文件更不容易
   被遗忘/散落）。

### 1.3 权限隔离与沙箱机制：是否有利用价值？

**开发者判断**（大意）：AGH 的权限隔离/沙箱机制（哪些工具需要审批、哪些文件路径
  读/写受限、daemon 沙箱级别等）对比赛交付本身不太重要，可以先忽略。

**现状核查**

- 项目现有的 `SKILL.md`（已核实，见其中那条"This rule exists because the
  project's reliability guarantee comes from **deterministic code actually running**, not
  from the model claiming it would have produced the same result — a permission short..."）
  已经**间接**用到了 AGH 的权限审批机制：它把"确定性脚本真的跑起来并且结果被记录进
  `audit_logs`"定为可靠性保证的核心，隐含前提是这些脚本的调用需要经过宿主正常的工具
  审批/执行流程（而不是 Agent 自说自话"我已经跑过了"），这条设计本身没有主动去利用
  沙箱层面的更细粒度隔离（比如限制 Agent 只能写 `program-design/runtime/<task-slug>/`
  这一个目录、不能碰其他目录），而是靠 SKILL.md 里文字协议层的"你只能用哪些输入"
  清单（1.2 里查到的那条"The only inputs you may use..."）来约束，没有叠加宿主沙箱层面的
  强制目录白名单。
- 比赛交付的评审重点是"结果对不对、过程有没有被审计记录"，不评"权限设计做得有多
  精细"，所以现状（协议层文字约束、没用宿主沙箱强制隔离）跟评审目标是匹配的，
  不需要为此多花功夫做沙箱配置。

**缺口分析**

- 没有缺口需要补，但需要在共识备忘录里**明确记录**这条"有意不用宿主沙箱做目录级
  强制隔离，改用 SKILL.md 文字协议约束输入范围"的选择及理由（跟 1.2 一样，这是一条
  "没被写进共识"的既定选择，不是疏漏，是当时的判断——理由就是开发者说的"对比赛
  交付不太重要"，但这条理由目前只存在于本次对话里，没进任何文档，以后如果有外部评审
  问"你们为什么不用 AGH 的沙箱功能来加固"，会没有一份写好的说明可以指过去）。

**建议方案**

- 在 `project_consensus.md` 里加一条简短的"权限隔离：本项目的选择与理由"说明：明确
  写"本项目没有利用 AGH 宿主层面的沙箱/目录白名单做物理隔离，理由是对赛制评审目标
  （结果正确性 + 审计可追溯性）而言这一层不是得分项；改用 SKILL.md 里文字协议的输入
  范围约束作为主要防线；如果未来要提交给非赛制的、更严格的评审场景（比如要求证明
  Agent 无法越权写敏感路径），再单独评估是否需要叠加宿主沙箱层，当前不做"。这是
  把"有意不用"这个判断本身记录下来，不是新增任何代码/配置改动。

**实施代价**：1 条备忘录条目，约 5–8 行，无代码改动，无风险。

### 1.4 AGH 任务编排：能否用宿主自身的编排机制承载 1.1 提出的全流程规划？

**开发者原始想法**（大意）：跟 1.1（上下文管理/规划文档）相关，但问的是一个更具体的
  实现层面：AGH 自身的任务编排机制（比如它有没有原生的"步骤依赖声明""子任务派发"
  "条件分支"这类能力），如果有的话，是不是可以不用自己手写一份 md 规划文档，直接
  用宿主机制承载这件事，可能比自己维护一份 md 更方便？

**现状核查（引用实际文件证据）**

1. 本项目的执行流目前完全靠自己写的 `problem_state.json` + `stage` 字段（`node_1_spec` →
   `node_1_5_data_source` → `node_2a_routing` → `node_2b_modeling` → `node_3_report` →
   `node_4_render` → `done`）来驱动，每个节点之间靠"上一个节点写完自己的字段、下一个
   节点读整个 `problem_state.json`"来交接，这是一个**线性、手写状态机**，没有用 AGH
   宿主侧的任何"任务编排"原语（比如把每个节点声明成一个带依赖关系的子任务、或者用
   宿主自带的条件分支/并行执行能力）。这是事实，不是遗漏——AGH 官方 `docs/` 里目前
   没有一份"任务编排 API/DSL"的公开文档（按 `docs/guide/` 和 `docs/reference/api.md`
   里现有的功能清单核实，宿主提供的核心能力是"单条对话内的工具调用 + 权限审批 + 会话
   管理"，没有暴露一个让用户声明"先跑 A 再跑 B，B 失败走 C"这种 DAG/工作流的公开
   接口）。
2. 换句话说，**AGH 目前没有公开的、可以直接拿来当"任务编排引擎"用的机制**，本项目
   自己手写 `stage` 状态机这件事是**唯一**可行的做法（除非绕过 AGH 自己在外面再包一
   层编排引擎，但那会直接违反共识备忘录 §0 的"非侵入式扩展原则"——不允许在宿主外再
   造一套执行引擎来驱动 AGH 内的 Agent，会破坏"基于标准 AGH 实例可泛用"的定位）。
3. 不过 AGH 有一个可以部分借用到的机制：`SKILL.md` 本身就是宿主支持的"按描述自动
   触发加载"的能力（宿主在识别到某类任务时会加载匹配 description 的 skill）—— 这条
   跟"任务编排"不是一回事（skill 是"遇到什么情况该加载哪套规则"，不是"这套规则里
   各步骤按什么顺序执行、失败了走哪条分支"），但说明宿主层面唯一跟"流程"相关的能力
   是 skill 触发，跟 1.1 提的"全程规划文档"是**互补、不冲突**的关系：skill 负责"什么
   时候该启动这套治理协议"，规划文档（1.1 建议的 `planning_<task-slug>.md`）负责"启动
   之后，这具体一道题里每一步做到哪、有没有偏离"。

**缺口分析**

- 结论：AGH 目前没有可以直接承载 1.1 那条诉求（全流程规划/防偏离）的现成任务编排
  机制，这不是"没用好 AGH 已有功能"的问题，是"AGH 官方本身就没有公开这一层能力"
  的问题。所以 1.1 建议的手写 `planning_<task-slug>.md` 方案目前是唯一不违反"非侵入式
  扩展"原则的实现路径，跟"AGH 自身机制能不能利用上"这个问题的答案是：能利用的部分
  （skill 触发、工具审批/审计）已经在用，不能利用的部分（真正的任务 DAG/条件分支编排）
  官方目前没有提供，需要自建规划文档这一层来补齐，这是合理的架构决策，不是绕过了什么
  更好用但没被发现的官方功能。

**建议方案**

- 维持 1.1 的手写规划文档方案，不为此去等 AGH 官方的任务编排功能（目前没有证据
  表明官方 roadmap 里有这个能力，且等不到也不能阻塞本项目当前这条线）。
- 在共识备忘录里补一条说明："本项目刻意没有用宿主外的额外编排引擎驱动 SKILL.md
  里定义的 pipeline（会破坏非侵入式扩展原则），也没有用宿主内置的、目前并不存在的任务
  DAG 机制（该机制官方目前未提供）；全流程规划的承载物是 1.1 建议的 `planning_<task-
  slug>.md`，跟 SKILL.md 的 skill 触发机制是"何时启动"与"启动后每一步怎么走"的互补
  分工，不是二选一。"  这条要写清楚，防止以后有人看到 AGH 未来的某个更新版本加了
  任务编排功能，误以为"以前没用到是疏忽"。

**实施代价**：1 条备忘录说明，跟 1.1 的开放问题（规划文档粒度）绑定——如果 1.1 最终
  决定不做规划文档这条线，本条也跟着作废；如果做了，这条说明是 1.1 落地时一并要写的
  配套文字，无额外代码改动。

**开放问题**

- 是否需要现在就去 AGH 官方仓库的 `docs/` 或 changelog 里核实一次"任务编排"是否真的
  从未在任何版本里提供过（避免本次判断是凭"我印象里没有"而不是实际查过），如果
  查出来某个近期版本新加了类似能力，1.4 的结论要更新成"该能力已有、且是否值得为
  本项目现有的线性 pipeline 改用它的评估结论是什么"，而不是维持"官方没有、只能自建
  规划文档"的旧结论。
- **本轮新增的战略层顾虑（未决，已给出判断供参考）**："AGH 目前没有内置任务 DAG"这
  件事本身，是**我们（比赛项目）该去补的缺口**，还是**该交给 AGH 官方**（他们的
  fullstack 文档里已经在推 `subagent`，是不是说明他们自己也在往"多 agent 协作"这个方
  向做，我们应该等一等他们出官方方案，而不是自己手写一个可能跟他们未来官方方案不兼
  容的规划文档）？
  **判断（本轮给出）**：两个问题其实是不同的东西，不该混在一起权衡——
  - `subagent`（1.4 末尾已核实过）解决的是"要不要把某一步交给独立子会话去做"（横向的
    任务派发/并行化），不是"给当前这道题的多节点 pipeline 声明步骤依赖/条件分支"（纵向
    的单任务内部顺序控制），这两条轴不重合，`subagent` 目前/未来的成熟都不能直接替代
    1.1 提的"手写规划文档 + `problem_state.json.stage` 状态机"要解决的"单道题内部防偏
    离"这个问题，所以"等 AGH 官方把 subagent 做成熟"并不是"等官方解决任务 DAG 编排"
    的等量替代。
  - 但判断"官方到底会不会/什么时候出一个真正的单任务 DAG 编排引擎"这件事，本次仍然没有
    证据（1.4 的 grep 只查到 `subagent`，没查到"task DAG/workflow 引擎"这类词出现在任何
    AGH 官方文档里），所以"等一等"这个选项目前没有任何可依赖的具体时间点/路线图能支撑，
    只是一个方向性的猜测。比赛项目有确定的截止时间，不能把截止时间押在"官方某个版本
    是否会加某个我们查不到证据的能力"上。
  - 结论：倾向维持 1.4 原判断——**现在就该自建 1.1 那套手写规划文档 + 状态机方案，不等
    官方**。理由：① 这是唯一不违反 §0 非侵入式原则的落地方式（在宿主外造编排引擎会破坏
    泛用性定位）；② 官方未来即便加了真正的任务 DAG 引擎，1.1 的手写规划文档（本质是一份
    markdown 文件 + 一个 JSON 字段）也不存在"不兼容"风险——它不是锁死在某个宿主 API 上
    的，是项目自己的文件，将来官方出引擎了，最坏情况就是"两份东西并存、选一份用"，不存
    在"当初不该做、现在被官方方案推翻"的返工风险，因为规划文档记的内容（每个节点的预
    期/假设/偏离情况）跟未来官方引擎可能提供的"任务编排执行能力"本来就不是同一个层面的
    东西，前者是"人/Agent 可读的计划记录"，后者是"引擎的执行调度"，就算官方引擎真做出
    来，规划文档也不会因此变得多余（计划记录这层需求不会因为引擎调度能力变强而消失，
    反而引擎越复杂越需要一份人类可读的计划说明来解释"这些调度到底在干什么"）。
  - 唯一的实际成本是：如果官方未来真的出了，需要重新评估一次"要不要把规划文档这一层合
    并进官方引擎的配置里"，但这个评估成本很低（是文档级的合并/迁移，不是重写），不构成
    现在"先不做、等一等"的合理理由。
**已核实（本次已做）**：查了 `docs/` 下所有出现"subagent""orchestr""workflow""dag"
  "subtask""pipeline"的地方（`grep -ri`，检索范围内跳过的 2 个超大文件实际是
  `docs/assets/readme/trailer.webp` 和 `trailer.zh-CN.webp` 两个图片资源，不是文档，
  跳不跳它们不影响结论），结果：除 `fullstack.zh-CN.md`/`fullstack.md` 里列出的一个
  `subagent` 能力开关，以及 `reference/cli.zh-CN.md` 里 `agh doctor subagents [--repair]`
  这一条诊断命令外，**没有任何**一个文档页面讲的是"声明式任务 DAG/工作流编排引擎"这类
  能力。`subagent` 这个机制本身是"开一个独立的子会话去做另一件事"（对应本 Harness 里的
  `subagent_spawn`/`subagent_fork` 那类工具），跟"给当前这个物理题的 4 节点 pipeline
  声明步骤依赖/条件分支"是两回事——它解决的是"要不要把某一步交给一个独立子会话去做"，
  不是"这一步先跑哪一步后跑哪一步、失败走哪个分支"。结论：维持"官方没有可用的任务
  DAG/工作流编排机制，本项目的线性 pipeline 只能用 1.1 建议的手写规划文档 +
  `problem_state.json.stage` 手写状态机承载"这个判断，本次核实结果没有推翻它，只是补上
  了"subagent 这一条容易跟任务编排混淆、但实际上不是"的说明，避免下次有人看到 `subagent`
  这个名字就误以为已经有一个现成的编排引擎可以拿过来用。

### 2.2 质量校验：公式推导/程序仿真之后，量纲门禁等工具是否被 SKILL 协议约束到"必须调用"？当前 hooks 设计与官方功能结合度如何？

**开发者原始想法**（大意）：格式规范、业务逻辑、漏洞风险这几类质量校验，很可能主要靠 SKILL 协议去约束，让 Agent 在公式推导、程序仿真之后主动调用量纲门禁等工具。当前对 hooks 的设计如何？跟官方功能（工具注册/审批机制）结合得怎么样？实际解决物理问题时能不能保证被按要求调用？

**现状核查（引用实际文件证据）**

1. "必须调用"这一层，**SKILL.md 里已经写得比较硬**（已核实原文措辞）：`SKILL.md` 开头那段"You must execute the following hooks before advancing to the next pipeline node"明确列了 3 条：① 写完物理公式后 **MUST** 调用 `dimensional_gate.py`；② 退化边界用例用 `boundary_gate.py` 跑过才放行；③ 下游纠错配额 N≤3，超限必须触发退火回滚。这不是"建议调用"，是明确的 MUST 措辞，且每一条后面都跟着具体的脚本路径（不是抽象说"要做量纲检查"，而是指名 `program-design/hooks/dimensional_gate.py` 这个具体文件），Agent 没有"要不要调用"的自由裁量空间，只有"没被授权调用时怎么办"的自由裁量空间（那个空间已经被 §4 的"Permission Shortfall — Stop-and-Escalate"规则管住了，见下面第 3 点）。
2. "调用之后结果必须被记录"这一层，也已经写了：`SKILL.md` 里"Every external capability call (API, physics data, simulation execution, and every `program-design/hooks/*.py` invocation) must write a structured audit record via `program-design/hooks/audit_log.py`"—— 也就是说 hooks 被调用这件事本身是**可审计的**，不是"调没调用只有 Agent 自己知道"，而是每次调用都要往 `audit_logs` 里写一条带时间戳/参数/artifact_id 的记录，跟 1.3 那条"确定性脚本真的跑 + 记录进 audit_logs"的说法一致，本次把"每一个 hooks 调用都要写 audit_log"这个颗粒度确认得更具体了。
3. "官方功能结合度"这一层，需要澄清一个可能的误解：本项目的 hooks（`dimensional_gate.py`/`boundary_gate.py`/`ode_model.py`/`audit_log.py`/`make_report_figures.py`/`trace_visualizer.py`/`trace_capture.cjs`）**没有一个是通过 AGH 官方的"工具注册表"（tool registry）机制注册进宿主的**—— 它们全部是放在工作区文件系统里的普通脚本，靠 SKILL.md 的文字协议驱动调用（"你现在应该运行 `python program-design/hooks/dimensional_gate.py ...`"），跟 AGH 内置的、宿主认识的工具（比如本 Harness 里 `document_read`、`computer_use` 这类）不是同一类东西。AGH 官方提供了一个 `mcp-helper`/`plugin-helper` 的插件体系（`packages/package-manager/bundled-plugins/` 下已核实存在 `mcp-helper`、`plugin-helper`、`skill-helper`、`document-reader` 四个内置插件），理论上 hooks 可以包装成 MCP 插件注册进宿主，**但项目没有这样做**（依据见 2.3 的详细核查）。这不是"用错了"，是一个有明确理由的架构选择：consensus §0 已经写清楚"宿主兼容性：任何确定性脚本应以独立 Python 脚本形式通过工作区文件系统调用，不修改宿主代码底层机制"，把 hooks 做成宿主插件会引入"宿主版本升级时插件 ABI 兼容性"这一层新的维护成本，跟本项目"面向所有物理问题泛用"的定位（而不是"面向某一个 AGH 版本锁定"）不匹配。所以"跟官方功能结合度"的准确答案是：**结合点是 SKILL 协议层（宿主支持 skill 自动加载）+ 宿主工具审批/审计机制（宿主支持工具调用的审批流程和 trace 导出）**，而不是 hooks 本身注册进官方工具表；这个选择是刻意做出的，理由如上。
4. "格式规范/漏洞风险"这几类校验，现状是：**没有**单独的确定性钩子（没有"格式门禁""漏洞扫描门禁"这类脚本），`boundary_gate.py` 只查"物理极值退化行为是否符合预期"（finite/zero/nonnegative/monotonic/bounded_by 这几类期望值），跟"代码有没有格式化问题""有没有明显的安全漏洞（比如把用户输入直接拼进命令）"这两类完全无关。这几类校验目前**没有任何一道门在查**，只能靠 Agent 自律或者人工审查，跟量纲门禁/边界门禁这种"确定性脚本硬拦"的机制不是一类东西—— 也就是说，开发者这条提问里"格式规范、业务逻辑、漏洞风险"这个清单本身，目前只有"业务逻辑"（物理公式对不对、边界行为对不对）这一类被现有两个门禁脚本真正覆盖到了，格式/漏洞这两类**没有对应物**，这不是"用了但没说明白"的问题，是"这条需求压根没被现有 hooks 架构接住"的缺口。

**缺口分析**

- "必须调用"的强制力，目前靠的是**文字协议层**（SKILL.md 里的 MUST 措辞）+ **宿主审批机制**（脚本跑起来要经过宿主的工具审批，审批拒绝时触发 §4 停止-上报规则），这套组合在项目自己可控的执行范围内是闭环的（Agent 想绕过 SKILL.md 里写死的 MUST 措辞，本身就要在宿主审批这一层暴露出来，因为调用动作是宿主可见的）。**但在"有没有真的调用"这个可核验层面，目前还没有一个独立的验证机制**—— 也就是说，如果未来跑一次完整流程，想知道"这次任务里 `dimensional_gate.py` 到底被调用了没有"，只能去翻 `audit_logs` 找对应条目，没有一个像"合规检查清单"那样自动化的东西（比如一个事后运行的 `compliance_audit.py`，扫一遍 `audit_logs` 看该调用的 hooks 有没有全部出现），这是可以补但还没补的一个缺口，且补它的成本很低（一个纯只读脚本，不改任何现有代码）。
- 格式规范/漏洞风险这两类校验没有对应钩子，且**不应该**硬塞进现有 `dimensional_gate.py`/`boundary_gate.py` 里（那是物理正确性检查，跟代码质量检查是两回事，混在一起会让"量纲门""边界门"这两个概念的定义边界变模糊）。如果要补，应该是新增独立的钩子脚本（比如 `lint_gate.py`/`security_gate.py`），并在 SKILL.md 的 hooks 清单里对应加一行，跟现有两个物理门禁脚本并排，而不是塞进现有脚本。

**建议方案**

1. 新增一个独立的、纯只读的"合规审计检查"脚本（`program-design/hooks/compliance_audit.py`），跟 `dimensional_gate.py`/`boundary_gate.py` 并列但不属于同一类（前两个是"跑题的过程中实时验证物理对不对"，这个是"题目跑完之后，检查该调用的 hooks 是不是真的都调用过、audit_logs 里有没有对应条目"），由开发者在流程结束后（不阻塞主流程）跑一次，输出"调用清单 vs 实际 audit_logs 条目"的对照结果。这是把"必须调用"这条规则从"事前协议约束"补上一个"事后审计验证"，两层结合才真正把"有没有按要求调用"这件事变成可核验的事实，而不是只能靠信任 SKILL.md 里的措辞。
2. 格式规范/漏洞风险这两类校验，如果需要，**单独新增** `lint_gate.py`/`security_gate.py` 两个脚本（不在本轮实施范围，先记账），并在 SKILL.md 的 hooks 清单里加对应的一行说明什么时候该调用（"每次提交代码前"而不是"每个物理节点之间"—— 触发时机跟量纲门禁/边界门禁完全不同，不能照抄那个节奏）。
3. 共识备忘录 §5 里已经写进的那条"hooks 没注册成宿主插件是刻意选择"的判断，建议追加一句话补全理由（目前是隐含的，没有明说）："这样做的代价是 hooks 的调用完全依赖 SKILL.md 文字协议 + 宿主审批这一层，不依赖宿主内置的工具注册表；好处是项目不受 AGH 宿主版本升级时插件 ABI 变化影响，跟非侵入式扩展原则（§0）保持方向一致。"  这条追加是纯文档澄清，不需要任何代码改动。

**实施代价**：第 1 条（`compliance_audit.py`）约 50–100 行新脚本，纯只读，不改任何现有代码，低风险；第 2 条（lint/security 门禁）本轮不实施，只记账（在 `dev-notes/development_backlog_review_2026-10-09.md` 里加一条待办，跟已有待办并列，不单独新开文档）；第 3 条（共识备忘录补一句话）几行文字，无风险。

**开放问题**

- `compliance_audit.py` 应该在流程结束后由谁触发：是写进 `trace_visualizer.py`（Node 4）里作为一个可选的 `--compliance-check` 标志自动跑，还是保持独立、由开发者手动在流程结束后单独跑一次？倾向前者（跟 Node 4 现有的"生成 HTML 报告"动作绑在一起，不容易被漏掉），但这样会跟"Node 4 是纯只读导出"的既有铁律产生一点张力（合规检查本身是只读的，不修改 trace，只是读 audit_logs 输出一个对照结果，所以其实不冲突，只是要在铁律里明确"只读导出 + 只读合规对照"这两个都是只读，不产生新的写操作）。
- 格式规范/漏洞风险这两类校验，到底要不要做，还是明确"不做，交给代码评审/其他工具（比如通用 lint 工具）"—— 这一条需要开发者拍板（项目范围问题：本项目是物理科研 Agent，不是通用软件工程框架，把通用代码质量检查塞进这条 pipeline 里可能超出项目边界）。
- **本轮全量回顾新增提示**：本条第 3 点现状核查里"hooks 没有注册进宿主官方工具注册表/插件体系，是刻意选择（理由：不引入宿主版本升级时的插件 ABI 兼容性维护成本，跟 §0 非侵入式扩展原则方向一致）"这条判断，性质跟 1.3（不用宿主沙箱）、1.4/2.1（不用宿主任务 DAG）完全同构——都是"判断了刻意不用宿主某项能力、且要写下来防止未来误以为是疏漏"。1.3/1.4 对应的判断已经按 1.4 的建议方案写进了共识备忘录 §5（现在的 §5 是"权限隔离与任务编排：本项目刻意不依赖宿主高级能力——一条总判断"），但 2.2 这条同性质判断目前**只写在本条正文里，没有进共识备忘录 §5**（已核实备忘录 §5 现在的实际内容，只有沙箱、任务编排两条，没有"hooks 不注册进宿主插件体系"这一条）。按 1.3/1.4 已经确立的处理先例（这类"刻意不用"的判断应该进共识备忘录，防止未来误读），本条这条判断也应该同样写进 §5，跟沙箱/任务编排并列为第三条——但按之前 1.3/1.4 写进备忘录是先跟你确认才执行的模式，本轮只把"该写、怎么写"记在这里，不直接改备忘录，等你确认。

### 2.3 MCP 和 AGH 插件功能：目前有没有用到？没有的话，之前"向外接取数据库/其他功能"的需求是怎么解决的？

**开发者原始想法**（大意）：这块目前好像没有做到。没有的话，之前提出的"向外接取数据库、其他功能"这类需求是怎么解决的？

**现状核查（引用实际文件证据）**

1. **官方内置的 4 个 bundled plugin**（`packages/package-manager/bundled-plugins/`，已核实全部存在）：`document-reader`（PDF/DOC/ZIP 等文档附件解析，这是宿主自带的、跟物理题无关的通用能力，本项目没有主动"接入"它做物理数据源，只是在 Agent 需要读外部 PDF 报告时会用到它，这是宿主自带的默认能力，不需要项目做任何额外配置）、`mcp-helper`（帮用户在 AGH 里注册/管理 MCP server 的工具本身，不是一个实际连到某个外部数据源的 MCP server，是一个"帮你连"的助手工具）、`plugin-helper`/`skill-helper`（帮用户创建/安装插件和 skill 的通用脚手架工具，跟物理项目内容无关，是宿主工具层的东西，本项目没有用到它做过任何事）。

**缺口分析**

- 没有需要紧急补的缺口（MCP 这条被明确判过"不是必须"，且替代方案已经跑通），但有一条跟 1.2 里"资产分类"相关的观察值得记在这里：`mcp-helper` 这个官方内置插件的存在，意味着"以后如果某个细分领域的物理数据源只有 MCP 形式才好用（比如某个专业数据库官方只提供 MCP 接口、不提供 HTTP API/静态文件），项目需要临时起一个本地 stdio MCP server 包一层"这件事，在技术上是现成可用的（宿主自带这个助手工具），不需要从外部引入新依赖—— 这一条目前没有被写进任何文档（包括 `data-source-routing.md` 的"Optional enhancement"那段），建议在 2.4 的"数据源名录拓展方案"里带一句，作为"遇到只有 MCP 形式的数据源时该怎么办"的既定应对，避免到时候重新临时评估一次。

**建议方案**

### 2.5 SKILL.md 的组织形式：单 skill 还是"主 skill + 子 skill"集群？要不要打包成 AGH 官方插件？

**开发者原始想法**（大意）：项目本体主要靠 `program-design/` 文件夹里的资产 + 一份 `SKILL.md`；这份 `SKILL.md` 是否臃肿？是否失去了 AGH SKILL 三层渐进披露的优势（AGH 是不是三层、还有没有其他值得利用的特色）？有没有别的形式可以交付，比如做成一个 `physics-agent` 插件、下辖一系列子 SKILL（例如：`p-a-所有步骤都应该参考的执行大纲`、`p-a-问题分析`、`p-a-报告撰写`、`p-a-绘制图表`）？这样做能不能更好地利用 SKILL 渐进式披露的特性提升 AI 效果？

**现状核查（引用实际文件证据）**

- 本条（2.7）问的是"**AI 实际跑一道新题时，自己能不能知道手头有哪些现成的 py 程序/数据源/模板可用、这道题该用哪个**"——运行时资源可发现性（run-time discoverability），跟清单里列没列库是两回事：库列进 `requirements.txt` ≠ AI 在 Node 1.5（数据源路由）判断"这道题该用 `poliastro` 还是手写轨道传播代码"时能知道"我们有 `poliastro` 可用"这个事实。

**现状核查（引用实际文件证据）**

1. `program-design/knowledge/` 目录下 8 个文件（`atmosphere-drag-ode.md`、`boundary-verification.md`、`data-source-routing.md`、`parameter-sensitivity.md` + 本轮 2.5/3.1 新加的 `permission_shortfall_protocol.md`、`pipeline_example_walkthroughs.md`、`report_structure_guide.md` + 一个 `space_diving/` 子目录）—— 这些是"方法论模板"，`data-source-routing.md` 里的 Level 0–Level 3 分层规则确实教了 Agent"遇到数据源需求时按 Level 0（本地已装包）→ Level 1（公开 API）→ Level 2（静态数据表）→ Level 3（解析近似）逐级判断"，**但没有任何一份文档告诉 Agent"Level 0 这一层里，当前环境里实际装了哪些包、各自覆盖什么物理量的什么范围"**——`data-source-routing.md` 里举例用的是 `ambiance`/`pymsis`（`requirements.txt` 注释里确认过这两个是"装好了但当前没有任何 hook 实际 import"），Agent 读到"Level 0 检查"这一节时，知道的是"方法"（怎么判断一个包在不在、覆盖范围够不够），不知道的是"候选清单"（该从哪里查"到底有哪几个包现成可用"）。
2. `requirements.txt` 本身（本轮 2.6 已经改过一版）是**最接近"资源目录"的东西**，但它现在的组织方式是按"依赖声明"排的（`sympy`/`pint`/`numpy`/`scipy` 一条一行 + 用途注释，末尾"按需引入"区列出 `poliastro`/`statsmodels`），**不是按"物理问题类型 → 现成有哪些工具/数据源"反查的方式**——一份 Agent 拿到新题时能用的目录，应该是"题目属于哪个物理细分领域 → 这个领域现成可用的库/数据源/模板清单"，`requirements.txt` 现在是"库的依赖声明 + 用途注释"，方向反了（"我装了这些库、各自干什么用"，而不是"这道题该查哪几个候选资源"）。
3. `dev-notes/第三方数据/` 顶层的 `README.md`（已核实，2.4 条目里引用过）逐个列了 5 个已接入数据源的字段说明—— 这份文档**方向是对的**（按"哪个数据源、什么领域、怎么用"组织，不是按依赖声明组织），但目前只覆盖了 5 个"已接入"的数据源，**没有**把 `requirements.txt` 里的 Python 包（比如"天体力学题该查 `poliastro`""热力学题该查 `scipy.integrate.odeint`"）跟这份数据源目录合并成一份"物理细分领域 → 现成资源（代码库 + 数据源 + 模板）"的总目录。也就是说，**"AI 靠什么知道这道题该用哪些现成资源"这件事，目前答案基本靠 Agent 自己在 `data-source-routing.md`（只讲方法、不讲清单）+ `requirements.txt`（讲库、不讲按题目领域反查）+ `dev-notes/第三方数据/README.md`（只讲 5 个数据源、不讲代码库）三份文件之间自己拼，没有一个入口把这三者合并成"给一道新题的完整资源清单"**。

**缺口分析**

- 这是一个**真实的、之前没有任何条目覆盖过**的缺口：1.2 讲的是"通用文件 vs 任务临时文件的目录分类"（文件放在哪里）；2.4 讲的是"数据源名录"（有哪些第三方数据）；2.6 讲的是"依赖清单里该不该列哪些库"（静态盘点）。**本条是第四类问题："AI 在运行时靠什么入口判断'这道题该用哪些现成资源'"，前三类都没有覆盖到"可发现性"这一层**。目前的实际效果是：`requirements.txt` 里明明列了 `poliastro`（虽然只是注释、没实际装），但 Agent 在 Node 1.5 判断天体力学题的数据源/方法时，**没有任何一份文档会把"poliastro"这个名字推到它眼前**（`data-source-routing.md` 里只提 `ambiance`/`pymsis` 作为 Level 0 举例，没有提 `poliastro`；`requirements.txt` 里那一行注释只有 2.6 本轮才刚加上，且不在任何 Agent 按协议必读的文档里——`data-source-routing.md` 没有指向 `requirements.txt` 的指针）。
- 跟 2.4 结尾"候选数据源名录"建议（要新增一份 `dev-notes/第三方数据/候选数据源名录.md`）是**同方向、该合并**的：2.4 那条只覆盖"第三方数据源"（CSV/API），没有覆盖"Python 代码库"（`poliastro`/`statsmodels`/`sympy` 这些）；本条的问题范围比 2.4 宽一层——**要建的是"按物理细分领域组织的、把代码库 + 数据源 + 方法模板三类资源合并在一起的目录"，不是 2.4 单独说的"数据源名录"这一类**。

**建议方案**

- 把 2.4 建议的"候选数据源名录"和本条的"运行时资源可发现性"合并成**一份**文档（不要分两份，避免又变成 1.2 里那种"同一件事散落在多份文档里"的问题）：新增 `dev-notes/第三方数据/资源目录（按物理细分领域）.md`，结构是"每个物理细分领域（天体力学/热力学/流体力学/... 跟 2.6 那张表的 8 个板块对齐）一节，每节列出：现成可用的 Python 代码库（名字 + 覆盖什么 + 来自 `requirements.txt` 哪一条 + 装没装）、现成可用的数据源（来自 2.4 名录）、现成可用的方法模板（来自 `program-design/knowledge/` 下哪一份）"。
- **不**新建一份单独的"可发现性机制"（比如让 Agent 在 Node 1 自动扫描 `requirements.txt`/`dev-notes/第三方数据/` 拼出一份"本次可用资源清单"）—— 那是 1.1/1.2 里"规划文档/资产分类"范畴的事，跟本条"缺一份按领域组织的资源目录"是两件事，本条只解决"目录本身"这一层，不额外发明"运行时自动发现"的机制（避免跟 1.1 还没落地的规划文档方案、2.1/1.4 已判断的"不用宿主任务编排"再次纠缠出新的耦合关系，跟上次全量回顾发现的问题 A 是同一类风险：新增一个"运行时自动做 X"的机制之前，先想清楚会不会又跟 1.1/2.2/3.2 那批待落地项撞车）。
- 这份目录文档本身是**静态、人工维护的清单**（跟 2.4 的"候选数据源名录"同一性质），不进任何自动执行流程，只是给 Agent（和人）一份"这道题该查哪里"的直接入口—— 改动是纯文档，不碰任何 Python/JS 代码，不影响 1.1/2.2/3.2 那批待落地项的执行。

**开放问题**

- 这份"按物理细分领域组织的资源目录"具体建不建、以及跟 2.4 建议的"候选数据源名录"合并成一份还是保持两份，需要跟 2.4 那条的"哪个细分领域最可能先出题"那个未决判断一起做（两条现在是分开挂着的待办，实际执行时会互相牵连，本条点明这个牵连关系，方便后续一起决策，不重复决策内容）。
- 2.6 本轮刚在 `requirements.txt` 里加的"用途注释"（比如 `poliastro` 那条）是"库→用途"的单向信息；本条建议的目录是"物理领域→可用库"的反查信息，方向不同、不冲突，但如果两份信息都真实存在且各自维护，未来改了一处忘了另一处的风险跟 2.5 查出来的"§7 跟 §2 重复、没有标注以哪段为准"是同一类问题—— 建议目录文档里对每个库/数据源只写"名字 + 指针（去哪看完整说明）"，不复制 `requirements.txt`/`data-source-routing.md` 里的原文说明，避免又造出一处"两处各写一遍"的新案例（跟 2.5 已经修掉的 §7 重复问题是同一个病根，这次是预防不是修复）。

### 3.1 学习竞赛范文的研究思路：把"行文逻辑"提炼成对 AI 流程约束的一部分

**开发者原始想法**（原文）："对范文的利用，除了学习其公式、图表、推理过程，还可以学习其整篇文章的行文逻辑，选择性地吸收进我们项目对 AI 模型的流程约束与指导中。"

**现状核查**

1. `dev-notes/reference-solutions/例题/` 目录下**已有** 3 份较完整的范文 txt 版本（2010-GM-B-210、2020-GM-A-340、2023-GM-A-131，各自 20–50 KB 文本，非空文件）以及 5 份 2025 年范文的 mineru 解析结果（各 1–4 MB，含图表解析）。这些文件已存在项目里，不是"还没有"。
2. **但没有任何一份项目文件（`SKILL.md`、`problem_state_template.json`、`program-design/knowledge/` 下任何模板）提到过"学习范文的行文逻辑"这件事**——`SKILL.md` Node 3（报告撰写）目前只有**结构约束**（"每个节点结束后追加什么内容"），完全没有**行文逻辑约束**（"怎么把多个节点的内容组织成一篇连贯的、有说服力的物理研究报告"——即"先给结论再给推导"、"假设要集中编号"、"验证章节必须独立于建模数据源"这类从范文里才能提炼出来的写作规范）。这是一个真实的缺口，跟 2.5 查出的"SKILL.md 内部没做够分层"是同一类问题：现有文档告诉 AI"每个节点该做什么"，但没有告诉 AI"最后写出来的报告应该长什么样"。

**缺口分析**

- 没有一份文档把"报告章节应该按什么顺序组织"这件事写清楚，AI 在 Node 3 撰写最终整合报告时只能凭直觉（或上一次运行时的残存上下文）决定顺序，缺乏可复现的、跟范文对齐的结构规范。

**本轮已执行**

1. 新建 `program-design/knowledge/report_structure_guide.md`（1622 字符），提炼了三份范文（2010/2020/2023）共同的 8 章标准结构（摘要→引言→假设→建模→验证→结果→优缺点→讨论），以及 3 条行文风格约束（结论先行、假设集中编号、验证独立于建模数据源）。文档末尾有一段"边界说明"，明确它只是方法论框架，不提供任何具体题目的数值/公式，§5 隔离规则对本文件继续有效。
2. `SKILL.md` Node 3 末尾加了一句指针（"撰写最终整合报告时，章节顺序参照 `report_structure_guide.md`"），没有改动 Node 3 原有的增量写作规则（"每个节点结束后追加一小节"这个机制不变），只是在"最终整合时应该按什么顺序组织"这一层补了一个有据可依的参照。

**开放问题**

- 目前提炼的 3 份范文是 2010/2020/2023 的（`.txt` 版本，文本质量较可靠）。2025 年的 5 份范文只有 mineru 解析结果（`.md`，每个 1–4 MB，含大量图片描述文本），**本轮没有从 2025 年范文里额外提炼结构**（文件太大，且 mineru 输出里公式渲染结果不稳定，提炼"行文逻辑"的价值边际不大——8 章标准结构在 3 份范文里已经足够一致，不需要再加 5 份来验证）。如果未来发现 2025 年范文在结构上有明显不同的新趋势（比如新增了"不确定性分析"章节），再补充进这份指南，本轮不做预判。
- 3 份范文的 txt 版本里，公式是以纯文本近似形式出现的（不是 LaTeX），读的时候需要手动对照理解；这不是本轮要修的问题（那是 3.2 LaTeX 渲染问题的范畴，见下条），但会影响"从 txt 版本里读范文"的体验，未来如果有需要可以补一份 LaTeX 版本的范文（非本轮范围）。
- **本轮全量回顾新增提示**：本条提炼出的第 7 章（优缺点）/第 8 章（讨论/未来方向）在内容性质上是**前瞻性判断**层（"什么条件会改变结论""哪些假设放宽会显著改变结果"），跟 1.1 规划文档（如果最终落地）里"预判方向/预判要用的方法"（1.1 建议方案第 1 条③，刻意只记"预判方向"、不预先写死具体数值结论）这一层是**同一性质的东西**——都在回答"事先预判了什么、跟预判相比后来实际发生了什么"。1.1 自己写的边界是"规划文档是过程记录，报告是结果叙述，两者分开，报告里可以两者都用但标注来源不同"，但当时（1.1 落地那轮）还没有 3.1 这份指南，没有把"报告第 7/8 章里要写的前瞻性判断"跟"规划文档里记的前瞻性预判"这两层重叠关系点出来。如果 1.1 的规划文档最终落地，建议明确约定：**规划文档里的"预判方向"字段和报告第 7/8 章里的"什么条件会改变结论"内容应该是同一份文字（规划文档是过程记录时的原始预判，报告第 7/8 章是该预判在结果出来之后回过头对照"哪些预判成了、哪些没成、为什么"的回顾性表述），而不是两份各自独立写的前瞻性判断**——否则同一个任务会留下两份平行的、可能互相矛盾的"预判"记录，跟 1.1 自己强调的"跟 `hypothesis_layer`/`verification` 字段的数值结论不冲突、只做对齐检查"原则会打架（现在会多出一个"跟谁对齐"的新对齐对象）。这条提示本身不改 3.1 已经写好的 `report_structure_guide.md`（那份文档不需要动，它只讲结构顺序，不讲"第 7/8 章的内容应该从哪里来"），只在"1.1 规划文档最终落地时"需要把这一层对齐关系一并考虑进去，本轮不做，记在这里。

### 3.2 LaTeX 公式不渲染的问题：会话界面 vs. HTML 报告，两个场景要分开判断

**开发者原始想法**（原文）："测试 4 中发现 AGH 会话界面、网页版报告中出现的 $latex 公式$ 都不渲染。也有一些 markdown 文本渲染失败。html 报告需要增加相应工具。会话界面则可能较难修改，你看看能否根据 AGH 官方指导，设计一个 AGH 插件实现？实现之后，需要写进项目相关设计备忘录，使得其他人拿到项目也能自动安装好这批显示补丁插件。"

**现状核查**

1. **HTML 报告（`trace_visualizer.py` 生成的产物）**：查全文（782 行），`_md_body_to_html()` 的 docstring 明确写着"$$-fenced math as plain `<pre>` — no LaTeX rendering, just readable text"——**这是刻意做的，不是漏掉了**。生成出来的 HTML 里没有任何 MathJax/KaTeX 引入（已核实，全文搜不到 `mathjax`/`katex`/`latex` 关键字）。这是"现在报告里的公式看起来是原始 LaTeX 源码，不是渲染后的公式"的直接原因，且是已知、有意的现状。
2. **会话界面（AGH 宿主自己渲染消息气泡的地方）**：查 `docs/` 下所有跟插件相关的文档（`plugins.zh-CN.md`、`frontend.zh-CN.md`、`capabilities.zh-CN.md`、`limitations.zh-CN.md`），**没有任何文档提到宿主的消息气泡渲染器支持（或允许第三方扩展支持）LaTeX 公式渲染**。前端插件机制（`frontend.zh-CN.md`）能做的事情是"往 `ui:sidebar` 这类槽位里注入一个独立 UI 组件"，不是"改造宿主内置消息气泡里的 markdown 渲染逻辑"——也就是说，**做一个 AGH 插件去"让会话界面里的 $x^2$ 也渲染"这件事，在当前 AGH 机制下没有可实现的路径**：插件够不到宿主消息气泡内部的 markdown 渲染器。
3. **本轮没有实际修改 `trace_visualizer.py`**（详见下面"为什么本轮不执行"），只在 `git status` 里确认了这个文件目前是干净的、跟仓库里已提交版本一致（即之前"没改过"这个判断是核实过的，不是我凭印象说的）。

**缺口分析 / 判断（区分两个场景，不混为一谈）**

- **场景 A：HTML 报告里的公式渲染——这个能修，且应该修。** 理由：`trace_visualizer.py` 生成的 HTML 是**本项目完全自己控制的产物**，加一段 KaTeX（自包含、无外部 CDN 的话需要把 JS/CSS 内联进 HTML；用 CDN 的话只是一行 `<script src>` 引入，带 `onerror` 回退，离线打开时公式退化为可读的原始 LaTeX 源码显示，跟现在的体验相比是纯改善，不会让页面崩溃）。这是一个 20 行以内的改动（往 `render_html()` 的 `<head>` 里注入一段标准 KaTeX 引入 + 回退脚本），不引入任何新的项目依赖（`katex` 不需要进 `requirements.txt`/`package.json`，它是浏览器端运行时资源，不是本项目 Python/Node 代码的依赖）。**本轮没有做**，原因见下面"为什么本轮不执行"。
- **场景 B：会话界面里的公式渲染——当前 AGH 机制下没有可靠的实现路径，不应该假装"能做成插件"。** 具体：前端插件槽位机制覆盖的是"给工作台加一块新界面"，不是"改造宿主内置消息气泡的 markdown 渲染器"（已核实 `frontend.zh-CN.md` 的槽位注册 API 只接受 `ui:sidebar` 这类独立槽位，没有"注入到消息正文渲染流程"这种 API）。**因此"设计一个 AGH 插件让会话里的公式也渲染"这个诉求，在当前 AGH 的能力边界内是做不到的**，不是"暂时还没做"，是"按现在的插件机制根本够不着那个位置"。这个问题应该记为"依赖 AGH 官方未来是否原生支持公式渲染"的待跟踪项，不应该被包装成"我们能用插件解决"。
- **"实现之后写进设计备忘录，让其他人拿到项目也能自动安装好"** 这句诉求，针对场景 A（HTML 报告）是可以直接落实的（改动本身就是加进 `trace_visualizer.py` 这个已经在项目里的文件，不需要额外的"安装插件"步骤——别人拿到项目跑一遍 Node 4 就能自动拿到带公式渲染的报告，没有"额外装一个插件"这一步）；针对场景 B，这条诉求在当前机制下没有可落实的对象（没有插件可以做这件事），所以备忘录里应该写的是"这条目前做不到、依赖官方、暂不解决"，而不是一个"已装好的插件清单"。

**为什么本轮不实际改 `trace_visualizer.py`（场景 A）**

开发者这条的措辞是"看看能否……设计一个 AGH 插件实现"，重点问的是**设计判断**（要不要做、能不能做成插件、做完要不要写进备忘录），不是"现在就动手写进 `trace_visualizer.py`"。场景 A 的修复本身很小（一段 head 注入），但它是改一个**已经在跑、被 self-tests 里多个测试用例依赖行为的**生产 hook（`trace_visualizer.py` 是 Node 4 的核心，改完要重新跑一遍 `dev-notes/self-tests/03/` 相关的验收脚本确认"公式加了之后没把其他渲染逻辑改坏"，这一步本轮没有做）。**改生产代码 + 没有对应的验收测试复跑** 不符合本项目一贯的"改一处、验证一处"节奏（跟 2.2 里核查出的"没有独立的事后合规核验机制"是同一个病根——这次是"改完没有主动跑一遍验证"，属于同类风险，本轮选择不冒这个险）。因此本轮把"场景 A 该不该做、怎么做"的判断写清楚、把"场景 B 做不了、为什么"写清楚，**不实际改动 `trace_visualizer.py`**，留给后续（跟 1.1/1.2 那批"先记账、后面统一落地"的策略一致，但比那批更明确：这里不是"要不要做还没定"，是"该做、但这一轮不想在没有验收复跑的情况下改生产 hook"）。
