## 二、为什么改了好几轮效果始终不理想——深层根因诊断

除了 `test6-1修正清单.md` 已经指出的现象外，本轮直接比对 `E:\agnes-harness` 下的代码、Skill 与知识文档，查明了导致“屡改屡败”的 **8 个系统性根因**（前 4 个为本轮源码核查新发现的深层病根，后 4 个为渲染与数据链路病根）：

### 根因 1（新核实）：测试区与开发源库脱节——“改在 `E:\agh-test`，未落 `E:\agnes-harness`”
- `test6-1修正清单.md` L153、L182 提到上一轮另一会话 AI 生成了 `E:\agh-test\...\test6rewrite.html`（含 `.report-files-sidebar`）并补了中文 `runlogs/*.txt`。
- 但本轮直接读取本仓库 `physics-agent/hooks/trace_visualizer.py`（937 行）、`physics-agent/knowledge/report_structure_guide.md`、`.agh/skills/*` 发现：
  - `trace_visualizer.py` 里根本没有 `.report-files-sidebar`，L549 仍是 `"<task-slug>"` 字面量，L587 `_katex_head_tag()` 仍返回 `""`；
  - `report_structure_guide.md` 仍只有“六条约束”（无第 7 条 B1）；
  - `physics-agent/hooks/skill_bom_check.py` 根本不存在。
- **结论**：上一轮修改没有沉淀到开发主仓库 `E:\agnes-harness`，如果在主仓库重跑或分发，所有旧 bug 会 100% 原样复现。

### 根因 2（新核实）：Skill 与知识库指令自相矛盾——AI 并非“不听话”，而是在照搬错误的旧指令
- `test6-1修正清单.md` 的 C1/C2 将“文件生成在工作区根目录或 `runtime/` 根目录、没进 `<task-slug>` 子文件夹”归咎于 AI 执行偏差。
- 但核查源码发现，**现有的 Skill 正文和脚本默认参数本身就在教 AI 放错位置**：
  1. `physics-agent/knowledge/path_convention.md` L29-35 规定路径为 `physics-agent/runtime/<task-slug>/report.md`；
  2. 但 `.agh/skills/physics-report-writing/SKILL.md` L17 却明确命令 AI：`append a short markdown section ... to the task's own report draft file physics-agent/runtime/report_<task-slug>.md`（直接放在 `runtime/` 根下！）；
  3. `.agh/skills/physics-agent-governance/SKILL.md` L22 写着：`written under physics-agent/runtime/ alongside the task's other artifacts`（同样指向 `runtime/` 根下！）；
  4. `physics-agent/hooks/trace_visualizer.py` L100-103 注释写着 `--report physics-agent/runtime/report_<task-slug>.md`，且 L907 `--out` 的默认值是 `"research_report.html"`（直接落在工作区根目录！）。
- **结论**：不把 `physics-report-writing/SKILL.md`、`physics-agent-governance/SKILL.md` 和 `trace_visualizer.py` 里这几处冲突路径彻底统一，光在别处加“严禁放根目录”的口号，AI 每次读到 Node 3/Node 4 原文还是会放错。

### 根因 3（新核实）：“1 插件 + 多 Skill”拆分半途而废，存在未清理的占位符与断头路由
- 检查 `physics-agent/plugins/physics-agent-orchestrator/index.mjs`（L9-15、L29-33）发现：尽管 `.agh/skills/` 已经拆出了 8 个子 Skill，**插件代码至今仍写着“当前拆分方案未定稿前（①第 4 点确认点 B 之前），唯一可读目标是一份完整的 `.agh/skills/physics-agent-governance/SKILL.md`”**，完全没有起到“插件提醒哪一步用哪个子 Skill”的设计作用（对应 `诉求对照表1013.md` 二-29）。
- 检查 `.agh/skills/physics-report-charting/SKILL.md`（L6、L12、L18）发现：文件开头仍顶着 `> **占位说明**：待③第 2 点定稿替换`，而主 Skill `physics-agent-governance/SKILL.md` L19 却写着 `③第 2 点已定稿（10/12），本指针不再占位`——主从文件状态不一致，导致 AI 读到子 Skill 时认为规则尚未定稿。

### 根因 4（新核实）：`path_convention.md` 的历史定论与 1011 侧栏蓝图正面冲突
- `physics-agent/knowledge/path_convention.md` L71-74 写着：`4d（trace_visualizer.py 的"本节所使用文件"块）里"运行记录"这个链接直接指向上面这个相对路径（浏览器点开即纯文本，不需要 JS 懒加载机制）`。
- 这段话直接违背了 `网页重新设计1011（开发者原文）.md` L25-31 的核心设计（“可点开名字到页面右侧窗格查看最终版代码与调用运行记录”）。只要 `path_convention.md` L71-74 不改，任何读了该文档的 AI 都会把文件做成外链跳转而不是右侧窗格内联预览。

### 根因 5：数据流向未厘清就改渲染层（双数据源不同步）
- `trace_visualizer.py` 的 `_section_files_block()`（L545、L556）渲染 `runlog-note` 时，实际读取的是 `problem_state.json` 里的 `audit_logs[].args.note`（英文），完全没有读取 `runlogs/<artifact_id>.txt`（中文）。
- 同时，Node 1.5 的 `data_source_decision` 直接写入了 `problem_state.json` 顶层字段，没有生成带 `script_path` 的 `audit_logs` 记录，被 L522 `related = [r for r in audit if "script_path" in r]` 直接过滤掉，导致“数据源声明”在网页上消失（或被硬塞进内部黑话字段）。

### 根因 6：KaTeX 自包含方案停留在假想目录 `vendor/katex/`
- `_katex_head_tag()`（L587-604）直接返回空字符串 `""`；`_js()`（L843）试图 `fetch('vendor/katex/katex.min.js')`。
- 但整个项目没有任何步骤创建或拷贝 `vendor/katex/`，且离线单文件 HTML 在浏览器 `file://` 协议下 `fetch()` 本地相对路径本身就会被 CORS 策略拦截！
- **结论**：即便创建了 `vendor/katex/`，在 `file://` 双击打开时 `fetch('vendor/katex/katex.min.js')` 依然会因为浏览器同源策略失败。必须将 KaTeX 的 CSS + JS（或 `<script>` 标签 / 内联 bundle）直接打进单文件 HTML。

### 根因 7：手写 Markdown 渲染器能力残缺
- `_md_body_to_html()`（L266-356）只写了管道表格（`|`）和无序列表（`- `）两个块级分支，其余所有行一律套 `<p>_inline(line)</p>`。
- 因此 `###` 三级标题、`>` 引用块、有序列表 `1.`、独立多行 `$$...$$` 公式块在 HTML 里全部退化为普通 `<p>` 段落。

### 根因 8：缺少强制执行的交付前自检闭环（E2）
- 报告写完或 HTML 重新生成后，没有一个确定性的 Python 校验脚本去拦截“未渲染的 `###`/`>`、源码态公式、死链、英文 `runlog-note`、开发黑话（`Level 0`/`Node 1.5`）、行内自言自语括注”，全靠 AI 自觉，导致带病交付。

### 根因 9（本轮对照 test6 产物新发现）：`report_structure_guide.md` 自身的措辞直接诱导了全部 4 处“AI 自言自语”
- 对照 `dev-notes/self-tests/06/测试生成文件/physics-agent/runtime/report_jupiter-moon-gravity-assist-decel.md` 与旧版 `report_structure_guide.md` 发现，开发者在 `test6-1开发者反馈.md` 中批评的 4 处“AI 自言自语”**100% 是 AI 照抄旧版 `report_structure_guide.md` 原文的结果**：
  1. `题目（原样引用）：` ← 照抄旧版指南 L14 `题目原始表述（原样引用，不改编）`；
  2. `逐条列出（正文里用编号引用，不再临时引入新假设）：` ← 照抄旧版指南 L15 & L26 `逐条编号列出……正文里引用假设时用编号，不在正文里临时引入新假设`；
  3. `**独立于建模数据源的交叉验证**（与 data_source_decision.verification_baseline.independent_of = true 一致）：` ← 照抄旧版指南 L29 `（跟 problem_state.json 的 independent_of 字段一致）`；
  4. 报告末尾 `### 本轮执行说明` ← 照搬旧版指南第 6 条 L41-43 `如果某节确实需要一段"这一节是怎么来的/为什么这么组织"的说明，集中放在报告开头一段里说一次`！
- **结论**：如果不把 `report_structure_guide.md` 里这些诱导性括号和内部字段名删干净，AI 越“听话”就越会在报告里写自言自语！（已在 S1 中彻底根治）。

## 附录 C：E4 右侧常驻预览窗格 + E6 单一数据源（SSOT）设计要点

1. **为什么 E4 必须采用“HTML 内联数据池 + 点击切换右侧窗格”而非 `file://` fetch**：
   - 现代浏览器（Chrome / Edge / Firefox）在双击打开本地 `file://` HTML 时，任何 `fetch('./runlogs/xxx.txt')` 都会触发 `Cross origin requests are only supported for protocol schemes: http, https...` 并直接失败。
   - 因此要实现 1011 蓝图“左边点文件蓝链，右边窗格实时显示最终版代码、运行记录、数据源详情”，唯一 100% 离线可用的方式是在 `trace_visualizer.py` 生成 HTML 时，将该任务涉及的脚本源码、`runlogs/<artifact_id>.txt`、数据源说明、Skill 简介打包进 `<script type="application/json" id="artifact-payloads">`，左侧蓝链绑定 `data-artifact-key`，点击时由内联 JS 实时渲染到右侧 sticky `<aside class="report-files-sidebar">` 预览窗格中。
2. **E6 消除“双写不同步”**：
   - `trace_visualizer.py` 优先解析 `physics-agent/runtime/<task-slug>/runlogs/<artifact_id>.txt` 的结构化头信息与中文说明；同时在 E2 自检脚本中加入门禁：扫描 `problem_state.json` 的 `audit_logs[].args.note` 与 HTML 文本，若出现全英文句子或 `Level 0`/`Node 1.5` 等内部黑话则直接判不通过并阻断交付。

### 7.1 测试 2 至 测试 5 暴露的核心问题（排除已在 S1–S7 解决的项）

1. **【图表核心缺陷 1 — Test 5 实锤翻车】“近乎空白 / 贴边死线（Near-Blank / Flat Curve）”无门禁拦截，逼迫 AI 抛弃 `make_report_figures.py` 手写一次性脚本**
