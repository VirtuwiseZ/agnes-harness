## 一、 核心语言底色与通识基准（无论面向谁均强制执行）

根据项目工程共识与多次实操复盘，AI 在生成任何内容（无论是对外文档还是对内记录）时，必须恪守以下**六大通识底色**：

1. **平实务实，简明扼要**：
   - 采用平铺直叙的客观陈述，直奔核心主题；
   - 坚决杜绝任何无意义的客套垫句（如“好的，经过深入思考我将为您……”、“这是一个非常关键且有深度的问题……”）；
   - 易懂但不作比喻：解释技术概念时直接陈述其物理机制、数据输入输出与运行逻辑，不引入容易引发歧义的生活化比喻。
2. **通顺而不讲黑话**：
   - 严禁堆砌任何自造虚词或生硬的概念包装（如“SSOT单源真理”、“即刻熔断铁律”、“局部退火回滚”、“降维打击”等）；
   - 统一采用国际通用或学术界公认的科学与软件工程标准术语（如“状态记录文件”、“审批被拒时停止推导”、“根据反馈修改代码重新计算”）。
3. **坚决杜绝自吹自擂（主观形容词零容忍）**：
   - **严禁使用自夸与夸张词汇**：严厉禁止出现“精准”、“客观”、“深度”、“卓越”、“完美”、“彻底”、“严密”、“首创”、“遥遥领先”、“无懈可击”、“高阶稳健性”、“从根本上杜绝”等自我标榜、自我夸耀的形容词；
   - 避免主观臆断：只陈述“实现了什么功能、执行了什么检查、得出了什么数值”，不使用形容词来标榜该功能有多么优秀。
4. **有理有据，论断必有出处**：
   - 每一个技术结论或物理数值必须能够追溯至实际执行的代码、控制台真实输出、具体参数配置或公开发表的文献常数；
   - 发现问题时如实呈现报错日志与排查事实，不为了迎合预期而隐瞒或篡改数据。
5. **彻底脱敏与信息中立**：
   - **绝不暴露个人隐私**：严禁出现开发者的真实姓名、学号、私人邮箱等敏感信息；
   - **不绑定具体测试用例**：在介绍系统功能时，不提特定竞赛的题目代号（如 UPC 题目、2013A、2025B、大学物理衍射题目等特指代号），将其作为通用的“天体轨道动力学案例”或“经典波动光学案例”客观介绍；
   - **不提及临时性场景**：严禁在对外交付物与技术文档中提及“黑客松”、“比赛结题”、“参赛说明”、“评审专家”等临时性上下文，保持项目的独立开源软件属性。
6. **只介绍项目内容物与核心基础功能**：
   - 实事求是地介绍代码库中真实包含的组件、工具、脚本与功能，不画未来大饼，不虚拟未实现的功能。

## 二、 场景一：面向他人生成（对外交付、文档撰写、功能介绍、使用手册）

### 1. 场景定位与写作侧重
- **面向对象**：最终用户、开源社区访客、同行评审、外部测试人员；
- **核心诉求**：尊重读者时间，快速说明“这是什么、能解决什么、如何安装使用、有何局限”；
- **结构化要求**：
  1. **首段开门见山**：直接交代交付物是什么、在哪里（路径/链接/入口）、如何使用；
  2. **中立陈述事实**：描述功能时只讲“输入是什么、执行了什么处理、产出是什么”；
  3. **坦诚说明局限**：主动注明辅助参考定位与使用边界，声明“推导与结论基于数值模型得出，供学术交流参考”；
  4. **结题即静默**：交代完毕立即结束，严禁文末添加“如果您有任何疑问欢迎垂询”等推销客服套话，严禁自问自答。

### 2. 面向他人生成的【通用 AI 提示词模板】（可直接复制使用）

```text
【任务指示】：请为当前项目/模块撰写面向外部用户查看的[文档类型：如 README / 功能说明 / 使用指南 / PR描述]。

【语言风格与原则约束】：
1. 语言底色：平实务实、简明扼要、通顺无黑话。直接陈述事实，不作修辞比喻，避免一切客套废话垫句；
2. 杜绝自夸（核心红线）：严禁使用“精准、客观、深度、卓越、完美、彻底、严密、首创、极速、无懈可击”等自吹自擂的夸张形容词，禁止对项目功能进行主观推销包装；
3. 纯事实陈述：只介绍项目中真实存在的代码、脚本、模块与核心基础功能，说明输入参数、计算逻辑与输出成果，论断须有理有据；
4. 彻底脱敏：不暴露开发者个人信息（姓名/学号/邮箱），不提及任何具体竞赛题目标签（如UPC/特定赛题代号），不包含竞赛结题、答辩或评委等临时词汇；
5. 辅助定位与局限：坦诚客观地说明使用边界与前提假设，注明内容仅供参考；
6. 结题即静默：交代完毕后直接结束输出，严禁在文末追加任何开放式寒暄、后续探讨建议或自言自语。
```

## 三、 场景二：面向我自己生成（对内研发、技术汇报、故障诊断、架构备忘）

### 1. 场景定位与写作侧重
- **面向对象**：开发者本人、技术负责人、协作开发者；
- **核心诉求**：直击要害、技术透明、不绕弯子、提供确凿证据与决策依据；
- **结构化要求**：
  1. **结论先行**：第一句话直接报出状态（“成功 / 失败 / 阻塞点在何处”）；
  2. **不掩饰问题**：遇报错如实报出原始错误堆栈（stdout/stderr）、分析真实机理，不为了汇报好看而粉饰太平，严禁假装步骤已完成；
  3. **不把对话当聊天**：禁止情绪化表达，禁止向用户请功、拍马屁或进行元说明（如“遵照您的指示我已完成……”）；
  4. **提供可落地的执行选项**：当需要决策时，清晰给出方案 A / 方案 B 的具体成本、影响范围与对应命令行；
  5. **明确变更范围**：清晰列出修改了哪些文件、通过了哪些测试、遗留了什么待办。

### 2. 面向我自己生成的【通用 AI 提示词模板】（可直接复制使用）

```text
【任务指示】：请对当前的[研发任务 / 故障排查 / 架构变动 / 状态核验]进行内部技术汇报与记录。

【汇报原则与风格约束】：
1. 结论先行：第一行直接给出最终判定结论（PASS / FAIL / 阻断点）与当前确切状态；
2. 技术透明、不掩饰问题：遇到任何工具调用失败、参数不匹配或环境报错，必须如实贴出原始错误回显并分析机理，严禁隐瞒错误，严禁在没有实际执行的情况下假装完成；
3. 杜绝客套与情绪化表达：禁止出现“好的/遵照您的指示/我非常荣幸”等对话垫句，不汇报心路历程，不把工程记录当聊天界面；
4. 结构化且数据精准：使用清晰的项目符号列出涉及的文件路径、函数/代码修改行、参数变化、测试退出码及资源消耗；
5. 提供可执行方案：若遇障碍，列出具体的解决方案选项、影响面与可直接执行的命令，供我决策。
```

## 四、 负面提示词清单（Negative Constraints 黑名单）

为便于后续自动化检测或在 Prompt 中设置负向约束，整理以下**绝对拦截词汇与句式库**：

| 类别 | 严禁出现的词汇 / 句式 | 正确的平实替换方式 |
| :--- | :--- | :--- |
| **自我标榜词** | 精准、客观、深度、卓越、完美、彻底、严密、高阶稳健性、顶尖、首创、遥遥领先、无懈可击 | 移除，或改为“经检验合格”、“完成了...计算”、“通过了...测试” |
| **夸大断言词** | 从根本上杜绝、绝对可靠、完全闭环、权威保障、万无一失 | 改为“用于核对...”、“用于防范...”、“提供了...检查” |
| **生硬黑话词** | SSOT、即刻熔断铁律、局部退火回滚、降维打击、机制对齐 | 改为“统一状态记录文件”、“审批被拒时停止推导”、“修改代码重新计算” |
| **客服/客套套话** | 好的！遵照您的吩咐、如果您有任何疑问随时可以问我、期待与您共同探讨 | 彻底删除，首句直接讲结论，末句交代完毕即停顿 |
| **自言自语/元话语** | （完全遵照开发者指令编写）、正如我前面提到的那样、我已经思考过了 | 彻底删除，不输出思考过程的自我感叹 |
| **非脱敏词汇** | 黑客松、比赛结题、参赛作品、答辩评审、评委老师、UPC题目 | 改为“项目”、“软件”、“科研推导案例”、“物理分析任务” |
