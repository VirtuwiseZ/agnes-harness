
## 一、比赛本质
### 从解题转向研究——在有限时间内完成一次压缩版科研
- 先理解问题本身，再通过文献和资料建立背景认识，提出合理假设，建立物理模型，利用计算或实验进行验证，在发现问题后不断修正模型，最后将整个研究过程整理成一篇能够自洽论证的科学论文。
- 因此比赛的核心能力并不是“知道多少公式”，而是能否把一个模糊的现实问题逐渐变成一个**可以定义、可以计算、可以验证、可以解释**的物理问题。题目通常并不存在唯一标准答案，不同队伍完全可能从不同假设和模型出发得到不同结果，因此应当更加关注自己的模型是否合理、假设是否透明、结果是否得到验证，以及结论是否确实由前面的分析支持。
## 二、拿到题后的第一反应
### 先理解问题——不要一看到公式就开始计算
- 题目公布后的最初阶段，最重要的事情不是立即搜索论文或者写 Python，而是看明白：我们究竟研究什么**对象**，它受到哪些**因素**影响，最终希望**解释、预测还是优化**什么量，哪些**参数**可以直接获得，哪些参数必须估计，题目中哪些信息实际上暗示了某种**物理机制**。最好能够**尝试用一句话概括整个研究目标**，例如“研究 X 如何受到 Y、Z 等因素影响”，这样后续的文献检索、模型建立和计算才不会不断偏离题目。
- 在理解题目的同时，应迅速识别其中可能涉及的主要物理机制，并区分**决定系统基本行为**的主要因素和**只会影响精度**的次要因素。不要一开始就试图把所有现实因素全部加入模型，而应该先寻找一个足够简单、能够工作的**最简模型**，再通过后续分析证明哪些现实因素确实值得加入。
- **数量级**估算应该尽早进行。即使还没有正式推导，也可以先估计各物理量的大致大小，并判断哪些效应可能远大于其他效应；这种粗略判断既可以帮助确定研究重点，也可以成为之后检查程序和结果是否合理的重要依据。
## 三、文献检索
### 文献服务于问题——不是为了堆积参考文献
- 文献检索的目的不是尽可能多地收集论文，而是解决当前研究中真正存在的问题。通常应先形成自己的初步物理理解，再带着具体问题搜索，例如某种现象过去是如何解释的、是否存在经典模型、某个参数通常处于什么数量级、有没有实验数据能够验证模型、自己的某个假设是否已经被前人研究过。
- 在检索工具上，可以形成“**AI 学术搜索 → Google Scholar → arXiv → Connected Papers → 全文获取**”的链条：当不知道应该使用什么关键词时，可以让 AI 学术搜索帮助自己发现研究方向和术语；已经明确关键词后，以 Google Scholar 进行广泛检索；对于物理学领域的新研究和预印本，再重点查看 arXiv；找到真正关键的论文以后，再利用 Connected Papers 向前寻找经典工作、向后寻找后续研究以及向旁支寻找相近问题；最后通过Unpaywall、南航数据库、Google Scholar 的 `All versions`、arXiv 等渠道获得全文。
- 论文不需要从头到尾全部精读。面对大量候选论文，应优先判断它**研究了什么问题**、使用了什么**模型**、得到了什么**结论**，以及其中究竟有什么东西可以帮助解决自己的 UPC 题目。真正进入论文正文后，再重点寻找**公式、实验数据、参数来源、模型假设**和可以用于比较的**结果**。
- 要警惕“文献搜索本身变成任务”的情况。只要已经拥有足够支撑当前模型的背景资料，就应该**停止**无限寻找“更好的论文”，**转回**自己的物理问题。
## 四、建立物理模型
### 从最简单模型开始——先让整个研究跑起来
- 建模的第一目标是尽快得到一个能够运行的 **Version 0.1 模型**。首先明确变量和参数，然后给出必要假设，再建立控制方程并进行粗略求解，最终得到第一版结果。这个结果即使很粗糙也没有关系，因为它最大的价值是让团队第一次看到系统的整体行为，并暴露接下来真正需要研究的问题。
- 有了第一版模型以后，再逐层**增加复杂度**。例如先建立理想模型，再加入最重要的现实因素，之后才考虑那些确实会明显影响结果的次要因素。每增加一个因素，都应该问自己：“它真的显著改变结果吗？有没有物理或实验依据支持加入它？增加的复杂度是否值得？”如果加入某个因素以后结果几乎没有变化，那么复杂模型未必比简单模型更有价值。
- 模型应该不断接受检验，而不是建立之后直接相信。可以通过极限情况、数量级分析、已知理论、实验数据、已有论文以及参数变化来检查它；尤其要观察参数改变以后结果是否符合基本物理直觉。如果结果异常，首先应该重新检查**物理假设和控制方程**，其次检查**参数和单位**，最后才检查**程序本身**。
## 五、计算与编程
### Python 是研究工具——不是为了展示技术
- Python 等计算工具最适合用来完成重复计算和人脑不容易处理的分析，例如数值求解、参数扫描、数据拟合、敏感性分析和绘图，但程序本身并不是研究成果。不要为了让模型看起来“高级”而主动使用复杂算法，真正值得计算的是那些能够回答题目问题、验证模型或者揭示物理规律的内容。
- 与其得到大量没有解释的数字，不如得到几张真正能够说明问题的图。例如**参数与结果之间的关系**、不同**模型的比较**、**理论值与实验值**的差异、**误差**随参数的变化，或者某个系统存在的**临界条件**，都比单独给出一个最终数字更具有研究价值。
- 计算过程应保持可追溯性，至少记录**重要参数的来源、单位、初始条件、模型假设和代码版本**。最终论文中的关键结果应该能够回溯到具体的计算过程，而不是出现“论文里有一张漂亮的图，但没人知道这张图到底怎么算出来的”的情况。
## 六、从“做题”转向“研究”
### 不断追问为什么——让模型产生研究深度
- 当第一版模型能够得到结果以后，研究才真正开始。应该不断追问“为什么这个模型成立”“它在什么条件下成立”“如果改变某个参数会发生什么”“有没有实验或文献可以验证”“在哪些情况下这个模型会失效”。这些问题会自然引导出参数敏感性、极限情况、不同模型比较、理论与实验比较、误差来源以及模型适用范围等更有研究价值的内容。
- UPC 中值得深入的地方往往并不是继续增加公式，而是寻找一个能够解释现象的核心规律。例如某个参数实际上只有在特定范围内才重要，某个常用近似只在一定条件下成立，简单模型与复杂模型在某个区域出现明显差异，或者理论预测与已有实验数据之间存在系统性的偏差。只要能够把这些现象解释清楚，研究就拥有了自己的内容。
- 最终应该形成一个明确的**核心发现**。论文不能只是“我们查了很多资料、建立了很多公式、运行了很多程序”，而应该能够回答“我们究竟发现了什么”。所有文献、公式、程序和图表最终都应该围绕这个核心结论服务。
## 七、比赛节奏
### 前期发散——中期收敛——后期冻结
- 比赛前期应该允许研究方向适度发散：快速比较不同解释、查阅背景资料、尝试不同的简化模型，并通过粗略计算判断哪些方向值得继续深入；这个阶段最重要的是快速建立对整个问题的认识，而不是追求最终答案。
- 进入中期以后必须开始收敛。当团队已经拥有一个能够工作的模型、一组初步结果和足够的文献依据时，就应该逐渐确定主要研究路线，并把时间集中在验证、改进和深化这条主线上。不要因为不断发现新的有趣方向，就在 48 小时里同时研究五六个问题。
- 大约进入比赛后半程时，应当建立明确的“**收口意识**”。如果已经能够回答题目的核心问题，就不要再为了显得高级而随意增加新的复杂模型；后期新增内容只有在能够明显增强结论可信度时才值得加入，否则更应该把时间投入到验证、图表、论文逻辑和表达上。
- 最后的几个小时应该视为论文审稿阶段，而不是继续科研探索的阶段。此时重点应该转向检查公式、单位、有效数字、图表、变量符号、引用、英文表达以及正文与程序结果是否一致，并尽量避免在最后时刻修改核心模型。
## 八、三人团队协作
### 分工是为了提高效率——不是把研究割裂成三块
- 比赛初期可以按照“**物理建模、文献资料、计算编程**”进行分工，让不同成员并行推进，但这种分工只是为了提高前期效率，不能演变成三个人各自做完全独立的工作。尤其到了中期，所有成员都必须理解当前模型、关键假设、主要参数和核心结果。
- 团队需要定期重新合流，把各自得到的信息放回同一个物理问题中。例如文献成员找到一个新的模型后，不能只是把 PDF 丢进群里，而应该说明这个模型为什么与当前研究有关；编程成员得到一张新图后，也应该解释它改变了团队对物理问题的什么认识。
- 最终论文应当由整个团队共同审阅。即使某个公式主要由一名成员推导、某段程序主要由另一名成员编写，每个人也应该能够解释论文中的核心内容，否则最后很容易出现研究成果无法真正拼接起来的问题。
## 九、论文思维
### 论文不是实验日志——而是重新组织后的论证
- 实际研究过程往往非常混乱，可能经历“模型 A → 失败 → 查论文 → 模型 B → 程序报错 → 模型 C”的反复尝试，但最终论文**不应该照着这个时间顺序记录**，而应该重新组织成读者最容易理解的逻辑：问题是什么 → 我们做了什么假设 → 为什么这样假设 → 建立什么模型 → 如何计算和验证 → 得到什么结果 → 为什么得到这个结果 → 模型有什么局限 → 最终回答了什么问题。
- 因此论文写作应该尽早开始，而不是等到最后几个小时才从空白文档开始。比赛中期就可以逐渐积累公式、图表、结果和参考文献，后期只需要把这些材料组织成完整的论证，而不是重新回忆两天里到底做了什么。
- 一篇好的 UPC 论文应该让读者即使不看代码，也能够理解模型是怎么来的、关键计算是怎么完成的、主要结果意味着什么以及为什么相信这个结果。代码可以作为研究工具甚至放入附录，但不能让代码承担本应由正文完成的物理解释。
## 十、最容易犯的错误
### 复杂化——不要为了高级而高级
- 一开始就使用 CFD、复杂数值算法或者其他高级工具，很容易让大量时间消耗在技术实现上，却没有真正增加物理理解。正确的顺序应该是先证明简单模型能够解释什么，再通过误差或实验结果证明哪里需要复杂化。
### 信息过载——不要让搜索取代思考
- 找到几十篇论文并不意味着研究进展良好。如果团队已经无法说清楚这些论文分别解决了什么问题，那么继续搜索通常不会产生真正价值。**文献应该围绕当前模型服务，而不是成为独立的任务**。
### 过度追求精确——先解决主要矛盾
- 如果某个参数的不确定性远小于模型本身带来的误差，就没有必要花大量时间把它精确到更多有效数字。UPC 更重要的是识别影响结果的主要因素，并把有限时间用在真正改变结论的地方。
### 无限探索——研究必须有截止点
- 开放题最大的陷阱之一就是“总还有东西可以研究”。因此团队必须**主动设置收口节点**：当核心问题已经得到合理回答，并且剩余时间更适合完善验证和论文时，就应该**停止扩展研究范围**。
## 十一、48小时总路线
### 从问题到论文——始终保持一条主线
- **0–2 h：理解问题并选择研究方向。** 两道题快速拆解，确定研究对象、核心变量和可能的物理机制，并选择最有可能在有限时间内形成完整研究链条的方向。
- **2–12 h：建立第一版模型。** 完成假设、方程、数量级估算和初步计算，让团队尽早拥有一个可以运行的模型和第一批结果。
- **12–28 h：文献、计算与模型迭代。** 查找经典理论和实验资料，通过 Python 进行参数分析，并根据结果逐步加入真正重要的现实因素，同时不断检查模型是否合理。
- **28–36 h：确定研究主线。** 明确核心结果、关键证据和最终论文要讲的故事，停止无休止地扩展方向，把剩余时间集中在证明和解释核心结论上。
- **36–46 h：完成论文并进行验证。** 整理模型、计算、图表和参考文献，检查理论与数据是否一致，并补充必要的敏感性分析、误差讨论和模型局限。
- **46–48 h：最终审稿与提交。** 不再进行可能破坏整体结构的重大修改，而是检查公式、单位、有效数字、图表、引用、英文表达、匿名要求以及论文和程序结果的一致性，并预留提交缓冲时间。
## 十二、最重要的一条思维链
### 从现实问题到科学结论——不要迷失在局部任务中
- 整个 UPC 研究过程可以始终压缩成一条主线：**现实问题 → 明确研究问题 → 背景调查 → 合理假设 → 最简模型 → 计算 → 验证 → 模型迭代 → 深入分析 → 核心结论 → 科学论文**。
- 当团队不知道下一步应该做什么时，可以重新回到这条链上判断：
	- 如果还没有理解问题，就不要急着计算；
	- 如果已经理解问题但没有模型，就开始建模；
	- 如果模型已经能够运行，就去验证；
	- 如果模型已经得到验证，就寻找能够产生研究深度的参数关系和边界条件；
	- 如果核心结论已经形成，就停止继续扩张，开始把研究整理成一篇能够让别人相信的论文。
