# 用户指定文件的解析工具：安装与调用参考

> 这是给 agent 的"照做参考"，不是协议本身——协议里只说"该用什么"，这里说"怎么装、
> 怎么调、本机边界在哪"。触发条件：当用户明确要求"参考某份 PDF/docx/图片文件"，且
> 该文件不是 agent 能直接读的纯文本时，按本文件的顺序走，不要凭记忆临时摸索。

## 第 0 层：先判断文件是从哪来的（决定走哪条链，不决定用哪个工具）

**两种来源，两条完全独立的判断链，不要混用**（这是 2026-10-08 官方 merge 后新
加的区分，见 SKILL §6）：

- **来源 A：会话附件**（用户通过 AGH 前端上传按钮传进来的文件，agent 看到的是
  `session-file://<seq>/<index>` 引用，可用 `read session-file://list` 列出当前
  会话里所有附件）。**只有这一条路能用官方 `document_read` 插件**（零本地 Python
  依赖，直接读附件字节，支持 PDF 嵌入文本/离线 OCR、DOC/DOCX、ZIP 先列名再按
  `entry` 取文件、纯文本；**不支持**磁盘路径或 URL，源码里是主动拒绝，不是暂
  时没实现）。
- **来源 B：本地磁盘路径**（用户说"我把文件放在 XX 目录里了"）。官方
  `document_read` **完全没有入口**（`path` 参数写死只接受 `session-file://`，见
  `packages/package-manager/bundled-plugins/document-reader/index.mjs` 的 schema
  正则 `^session-file://[1-9][0-9]*/[1-9][0-9]*$` 及源码里对非该格式的
  `DOCUMENT_REFERENCE_REQUIRED` 主动报错）——**这条路上 L1/L2 仍然是唯一可行
  路径，PyMuPDF4LLM 没有替代品，不能因为官方插件存在就删掉它**。下面
  L1/L2 两节只适用于来源 B；来源 A 走上面的第 0 层，不要跳过直接套 L1/L2。

**来源 A 特有的两个边界（2026-10-08 实测确认，不是猜测）**：
1. **`document_read` 只能读"附件已经被 agent 解析后的文本/页图"，拿不回
   原始 PDF 字节**（附件字节存在会话 ledger 的事件行里，不落磁盘；`session
   export` 导出 ledger 时会把 `file`/`image`/`base64` 类型的附件字节替换成
   `[OMITTED:binary:...]` 占位符，是刻意的隐私设计，不是遗漏）。所以**不
   存在**"把会话附件原样落盘、再喂给 L2 MinerU 做定点补全"的自动通道——
   如果来源 A 的文档在 Tier 0（`document_read`）读完后发现公式/关键表格/核心
   插图仍然读不出来、且确实需要走 L2，**唯一可行做法是请用户把同一份文件
   也存一份到磁盘目录（或直接给一个磁盘路径），再按来源 B 的 L2 流程跑**，
   不能用 `document_read` 的输出文本冒充"原始 PDF 文件"喂给 MinerU。
2. **公式理解能力上，`document_read` 和 L1 PyMuPDF4LLM 是同一档，都没有跨
   过"把公式转成可解析 LaTeX 结构"这道质变门槛**（2025-GM-A-112 实测：公式
   (2) 的 $H_{resonator}(s)$ 求和转移函数，`document_read` 拆成 13 行线性散
   字符，分子分母结构丢失；L1 同区域甚至整块缺失；只有 L2 MinerU 转成了
   标准 LaTeX 分式）。`document_read` 相比 L1 强在"公式区域的字符至少都被
   抠出来了（虽然散乱）"和"能按页渲染整页图（L1 完全没有抠图能力）"，但
   这两点都不构成"能替代 L2 判断公式是否读懂"的依据。**所以来源 A 的
   判断标准和来源 B 完全一致**：文档里"公式/关键表格/核心插图"坏区是不是
   恰好落在物理结论所依赖的位置上——是，就必须走 L2（且要先解决上面
   第 1 条"拿不回原始字节"的问题，即请用户另存一份磁盘路径）；不是，
   Tier 0 的输出足够，不用碰 L2。

## 分层总览

```
L1  PyMuPDF4LLM（默认第一档，纯文本/版式/表格，无公式理解）
   ↓（仅当 L1 输出的"坏区"落在公式/关键表格/核心插图上时才升级）
L2  MinerU basic 档（重量级，真正能读懂公式/图片；本机 4GB 显存只跑得动这一档）
```

pypdf 已评估并**不采用**（能力被 PyMuPDF4LLM 完全覆盖且更弱：纯文本流、无表格/
图片处理），不在任何一档出现，避免每次调用前多做一层"选哪个"的判断。

## L1：PyMuPDF4LLM

### 安装（仅首次调用时做，装过就不用再装）
```
pip install PyMuPDF4LLM
```
（会连带装 `pymupdf`/`pymupdf-layout`，版本 `1.28.x` 已实测可用。）

### 调用
```python
import pymupdf4llm
md = pymupdf4llm.to_markdown("<用户指定的文件路径>")
```
- 输出是纯 markdown 字符串：正文、标题层级、表格（pipe 行）都在里面；
  不会把公式转成 LaTeX（它没有公式理解能力，公式区域只会按字面位置抠出散字符）。
- 实测速度：4–5MB 的 PDF（约 25–110 页）在 6–25 秒之间，纯 CPU，不需要 GPU/显存。

### 已知坑（撞到了再处理，不是每次调用都要做的常规步骤）
若文档使用了数学花体/特殊符号字体（Fraktur 等），`to_markdown()` 返回的字符串
可能含孤立的 UTF-16 半 surrogate（`U+D800–U+DFFF`），直接 `open(..., "w",
encoding="utf-8").write(md)` 会抛 `UnicodeEncodeError`。本次项目实测 5 篇里 2 篇
（`2025-GM-B-127.pdf`、`2025-GM-B-796.pdf`）触发过，3 篇没触发——**不是每次调用
都会发生，撞到再处理**：
```python
import re
md = re.sub(r"[\ud800-\udfff]", "?", md)  # 只在校验/落盘之前做这一步，不报错就跳过
```
用 `?` 占位符而不是静默删除，跟项目"不许静默 paper over"的原则一致；代价是这几个
符号位置会显示成 `?`（本来就没被正确识别成 Unicode 字符，不是丢了真实内容）。

### 判断要不要升级到 L2
拿到 L1 输出后，自己扫一遍：
- 坏区（公式区散字符、断裂/乱序的表格、缺失的图）如果**不在核心结论上**
  （比如只是正文里一处不重要的示意公式），不需要升级，直接用 L1 结果继续分析。
- 坏区**恰好落在公式/关键表格/核心插图上**（物理题里"哪个量是多少"往往就藏
  在公式里，公式读不出来 = 这道题的核心结论没拿到），才升级到 L2。
- **不要因为是物理题就默认走 L2**——这是本次分层设计要避免的事："公式密集"
  判断的是文档内容，不是题目类型。

## L2：MinerU（basic 档，本机唯一可用档位）

> 本节仅适用于**来源 B（本地磁盘路径）**，见文首"第 0 层"。来源 A（会话附件）
> 拿不回原始 PDF 字节，无法直接喂给 MinerU（见第 0 层第 1 条边界）。

### 安装（仅首次调用时做）
```
pip install 'mineru>=4.0,<5'
mineru-kit models download --tier basic   # 下载 ONNX 模型，13 个文件，本机 CPU 推理可用
```
- `standard`/`advanced` 档需要 8GB+ 显存（PyTorch/vLLM 引擎），**本机 4GB
  显存（RTX 4050 Laptop）跑不了**，不要尝试本地调这两个档。
- 只有 `basic` 档能在本机跑（ONNX/CPU 引擎），速度约 75–340 秒/篇（视页数），
  这是"公式/图片密集"文档在本机的**唯一可用路径**，慢是结构性的，不是能优化
  掉的——**但"定点补全"（`--pages`，见下）跑的是"只解析坏区所在的那几页"，
  不是整篇重跑，实际耗时按页数比例缩小，不是每次调 L2 都要付 75–340s 全篇
  代价**。
- 想要更高档位只能走 `--remote`（上传到 mineru.net 官方服务器），**需要用户明确
  同意才能启用**（题面/范文可能涉及版权或隐私，上传是用户自己的决定，agent 不
  能替用户做）；本次项目 5 篇范文全部走本地 `basic`，没有走远程。

### 调用（用 `mineru-kit parse`，不用 `mineru` 的 doclib managed-server 路径）
```
mineru-kit parse "<文件路径>" -o "<输出目录>" --tier basic
```
- **"定点补全"能力（2026-10-08 新记录，此前本文件没有这条）**：`mineru-kit
  parse` 支持 `--pages`（`-p`）参数，格式如 `'1-5,8'`（页范围 + 逗号分隔的
  单页）、`'r3-r1'`（从倒数第 3 页到倒数第 1 页）、或 `'all'`（默认值，即整篇）。
  **典型用法**：L1 先跑完全篇、确认坏区只在第 8–10 页的公式区，跑 L2 时
  用 `--pages '8-10'` 只解析这几页，而不是重跑整篇（省掉全篇 75–340s 里绝大
  部分时间）。**但这条能力目前只核实过 `mineru-kit parse --help` 输出里确实
  有 `--pages` 参数，没有在本机实际跑过一次 `--pages '8-10'` 的定点补全**
  （历史 5 篇基准全部是 `--pages` 缺省=整篇跑的，见
  `dev-notes/self-tests/03/parser_benchmark_analysis.md`）——第一次真正用到
  这条能力时，先确认"输出的 md 里确实只有那几页的内容、没有偷偷跑成全篇"，
  再把它当成可信的省时间手段用；如果实测发现它静默退回整篇解析，把这一
  条改成"未验证/不可用"，并回退成把 L2 当纯整篇工具用。
- **格式边界（待实测，不要假设）**：`mineru-kit parse` 的输入默认是给 PDF
  用的（`--pages` 参数本身也是按 PDF 页码设计的）；**是否接受 `.docx` 直接
  作为输入，本项目从未验证过**——SKILL §6 的"格式覆盖对比"里把这一格标成
  "待实测"，撞到 `.docx` 需要走 L2 时，先用一个真实 `.docx` 文件实际跑一遍
  确认，再决定能不能用，不要靠猜。
- **不要用 `mineru server start` + `mineru parse`（doclib managed-parse-server）
  这条路径**：本机实测该路径反复出现"server 声称启动成功但下一次调用检测不到
  在运行"的问题（`mineru server status` 显示 `parse_server: null`），且查不到
  崩溃日志，原因未定位；`mineru-kit parse` 是无状态、不需要常驻 server 的等价
  命令（底层解析引擎相同），5 篇实测全部一次成功，是已经验证过的可靠路径。
- 输出是 `<输出目录>/<原文件名>.md`，公式转 LaTeX、表格转 pipe、图片内联为
  base64（体积会比 L1 大很多，这是正常现象，不是文件坏了）。
- 同一篇文档重复解析会命中 SHA256 缓存，几乎瞬间返回，只有"第一次解析某篇
  新文档"才是那个慢速度。

### MinerU 已知的小瑕疵（撞到再处理）
`2025-GM-B-796.md` 实测发现：内嵌 Python 代码块里以 `#` 开头的注释行，被误判成
markdown 一级标题（H1），会让"把这份 md 转成 HTML"这类下游步骤多出一堆错误的
大标题——**不影响物理正文内容**（代码和周围文字都是完整可读的），只在"这份 md
会被进一步转成 HTML 页面"的场景下才会暴露。目前项目没有这种下游场景，撞到
时按"已知瑕疵、不影响本次分析"记录即可，不用为此重跑。

## 本文件的触发边界（跟 SKILL 里新增的 §6 保持一致）

- **只有当用户明确要求"参考/读取某份文件"且该文件不是 agent 能直接读的纯文本
  时，才走这里的流程**——不是每次 agent 启动、也不是进入做题流程的固定节点。
- 用户只是给了一段文字题面（直接在对话里贴出来的），不需要走这里，直接分析
  就行；不要为"题面是文字"这件事去多装/多跑一遍文档解析工具。
