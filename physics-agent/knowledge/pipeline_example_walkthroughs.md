# Pipeline 节点规则的具体举例汇编（Examples & Walkthroughs）

本文档收纳 `SKILL.md` §2 里 Node 1a、Node 2a 两条规则里"具体举例"的内容。
`SKILL.md` 正文只保留这两条规则的硬规则本身（哪些字段必须写、什么时候必须做
什么检查、出现某类失败时必须怎样处理），把"比如某某情况下应该怎样判断"这类
举例说明独立收纳到这里，目的是让 `SKILL.md` 正文更聚焦于"必须执行的判断"，
举例仅供第一次理解规则时参考，不用每次都读。

## Node 1a（`internal_prior` 内部预判）举例

`SKILL.md` Node 1a 规定的两条硬规则是：（1）`internal_prior` 字段只能作为
"稍后跟实际结果对照检查"的参考输入，绝不能作为证据/结论出现在报告、HTML
或给用户的回复里；（2）`internal_prior` 不得被当成一个"已经算出来的结果"，
如果发现自己拿它的结论去填分析里的空缺（而不是重新走一遍 pipeline 自己的
门禁和验证），必须停下，因为这就是 §4 明令禁止的"用手写重放冒充真实运行"的
同一类失败模式。

具体举例（什么时候算"大偏离"、偏离了之后怎么处理）：

- 举例场景：Node 1a 里预判"这道题的主导物理过程应该是阻力控制的自由下落，
  终端速度量级应该在几百 m/s"，但 Node 2b 实际跑出来是"阻力项被数值误差放大、
  终端速度量级差了一个数量级"——这是"直觉判断错了"（正常，换个假设重跑
  即可，不算失败）；但如果 Node 2b 跑出来跟直觉一致（终端速度确实是几百
  m/s），而量纲门禁在中间某一步其实一直没通过（只是被忽略了、没有真正
  阻断后续步骤），"结果碰巧看起来对"不等于"过程是对的"—— 这种偏离
  （"结果对了但验证门禁其实没跑通"）才是 `internal_prior_divergence` 这条
  审计记录真正要捕捉的信号，必须展开调查，不能因为"数字看起来没问题"就
  放行。
- 另一类举例：如果某道题目（比如一道纯电磁学题目）根本没有需要"预判主导
  量级"的物理直觉可言（比如纯代数求解，没有明显的"应该先大后小"或"应该
  是某个量级"的自然判断），`internal_prior` 字段可以为空/省略，这不是遗漏
  —— 这条规则是"如果有预判就写下来"，不是"必须每道题都强行造一个预判"。

## Node 2a（模板机制匹配检查）举例

`SKILL.md` Node 2a 规定的硬规则是：匹配到一个模板之后，不能直接照它的步骤
跑，必须先做一份写下来的"机制匹配"检查（不是数值匹配）：在
`problem_state.json` 里写明这个模板实际是围绕哪个物理机制建的，再逐条核对
本题的给定条件是否真的实例化的是这个机制（不是仅仅"话题词看起来相关"）。

具体举例（"张冠李戴"这类失败长什么样）：

- 举例场景：`atmosphere-drag-ode.md` 模板是围绕"阻力主导、一维、变密度
  垂直下降"这个机制建的；如果一道题只是"从高处下落"（话题词重叠）但实际
  是辐射/烧蚀主导的再入问题，虽然高度范围跟模板的例子重叠，机制不是同一个
  —— 直接用这套模板的 CD/A 值、Mach 阈值判断，属于"张冠李戴"失败模式，
  这就是这条检查要抓的。
- 举例场景：一道题从头到尾没有跨过音速区（比如全程亚音速下降），那么
  模板里"跨音速前后阻力系数要分段处理"这个假设就没有适用的触发条件，不
  需要重新推导一个"本题的 Mach 阈值"，直接把这一整块假设标注为"从示例
  继承、本题不适用、已剔除"即可—— 不是每条假设都要重新推一遍，只是要
  能说明"为什么这条假设不适用于本题"。
